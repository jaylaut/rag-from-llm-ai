# P7 · Agent 基座开发指引

## 一、本阶段要做什么

一句话：**让系统从"你问我答"的问答机器，升级成"能自己思考、自己动手调用工具、自己规划步骤"的智能体（Agent）。**

这是整个项目的**终局和高潮**，也是简历上最有区分度的一笔——因为绝大多数教程只做到 RAG 就结束了。

💡 对比理解：
- RAG（P1~P6）：像图书馆管理员——你问，它翻资料，回答你
- Agent（P7）：像你的私人助理——你交代"帮我查 X 再算 Y 最后总结成报告"，它**自己拆解步骤、自己调用工具、自己判断做完了没**，最后交付结果

---

## 二、涉及的技术逐个拆解

### 2.1 Agent 是什么

**它是什么**：一个能"**自主决策、调用工具、多步执行**"的大模型应用。

**核心特征（和普通对话的本质区别）**：

| | 普通对话 | Agent |
|---|---|---|
| 能力 | 只会"说话" | 会"动手"（调工具） |
| 步骤 | 一问一答 | 自己规划多步 |
| 自主性 | 被动 | 主动（判断、循环、修正） |

---

### 2.2 Function Calling（函数调用 / 工具调用）—— 本阶段的基石

**它是什么**：大模型的一种能力——**模型不直接回答，而是"说"出"我要调用哪个工具、传什么参数"**，由你的程序真的去执行，再把结果喂回给模型。

**这是最关键的机制，务必理解** 💡：

想象你和一个助手对话，助手说"我需要查一下天气"，但它自己没手没脚，得靠你帮它执行：

1. 你告诉模型："我有这些工具：查天气、算数学、查知识库"
2. 用户问"北京今天多少度，适合跑步吗"
3. 模型**不回答**，而是输出一个"指令"：`调用 查天气(城市=北京)`
4. 你的程序**真的去查了天气**，拿到"25度，晴"
5. 把"25度，晴"喂回给模型
6. 模型再判断"需要算吗？不需要了"，然后输出最终回答"适合跑步"

**关键**：模型负责"**决策**"（该调什么、传什么参数），程序负责"**执行**"。两者配合，模型就"长出了手脚"。

**技术细节**：Function Calling 需要你把每个工具描述成 **JSON Schema**（一份"参数说明书"，告诉模型这个工具叫什么、要什么参数、参数什么类型）。qwen-max 支持这个能力。

---

### 2.3 ReAct 循环 —— 手写 Agent 的核心（本阶段重中之重）

**它是什么**：一种让 Agent 工作的经典模式，全称 **Re**asoning + **Act**ing（推理 + 行动）。

**三步循环**（这是理解 Agent 的钥匙）🎓：

```
① Thought（思考）：我现在该干什么？
        ↓
② Action（行动）：调用某个工具，传参数
        ↓
③ Observation（观察）：工具返回了什么结果？
        ↓
    （回到①，基于新信息继续思考，直到能给出最终答案）
```

**用上面的例子走一遍**：

1. Thought：用户想知道天气和是否适合跑步，先查天气
2. Action：`查天气(北京)` 
3. Observation：25度，晴
4. Thought：信息够了，可以回答了
5. 输出最终答案

**为什么必须手写（这是卖点）**：
- LangChain 等框架把这套循环封装成黑盒，你 `AgentExecutor.run()` 就完事，看不到内部
- **手写 ReAct**，你才能真正理解"Agent 到底是怎么一步步决策的"——面试官一问"Agent 底层怎么运作"，你能讲清楚

---

### 2.4 工具注册机制（Tool Registry）

**它是什么**：一个"工具箱"，管理 Agent 能用的所有工具，每个工具带"名称 + 描述 + 参数说明 + 执行函数"。

**为什么要有它** 💡：Agent 的能力上限 = 它有多少工具。注册机制让你能**随时给 Agent 加新工具**（联网搜索、查数据库、发邮件…），能力就不断扩展。

**每个工具包含**：
- **name**：工具名（模型靠这个名调用）
- **description**：干什么用（模型靠这个判断"该不该用"）
- **parameters**：JSON Schema 参数说明（模型靠这个"正确传参"）
- **func**：真正执行的函数

**RAG 如何变成工具**：把 P2 的检索封装成 `retrieve(question)` 工具 → Agent 就能"需要时自己检索知识库"。这是 RAG 和 Agent 的**无缝衔接点**。

## 三、RAG → Agent 的复用映射（承上启下的核心）

| RAG 模块 | 变成 Agent 的什么 | 怎么变 |
|---|---|---|
| 检索（P2） | `retrieve` 工具 | 封装成可调用函数 |
| 生成（P3） | 推理能力 | 复用 qwen-max + Function Calling |
| 编排（P5） | ReAct 循环 | 静态调度 → 动态自主决策 |
| 检索评估（P5 CRAG） | 工具结果质量判断 | 决定继续检索/换工具/直接答 |
| 索引（P1） | 长期记忆/知识库 | Agent 可检索的知识来源 |

**一句话总结整个项目**：P1~P5 把"零件"造好，P6 把零件组装成"产品"，P7 给产品装上"大脑"，让它从"问答"进化为"自主干活的智能体"。

### 3.1 一个概念要先对齐：Agentic RAG 🎓

**它是什么**：2026 年业界最大的范式转变——检索不再是"固定管线里的一步"，而是 **Agent 自主决策的工具调用**。Agent 自己判断"要不要检索、用哪个工具检索、结果够不够、要不要换方式再检索"。

**和本项目的对应关系** 💡：

- P5 编排层的"自适应路由（L0~L3）"就是 Agentic RAG 的渐进式路线——L2 多跳检索已是 Agentic 雏形，L3 就是完整 Agentic RAG
- P5 的 CRAG 检索评估器，在 Agent 语境下就是"工具返回结果的质量判断"
- **本阶段（P7）就是把 P5 的"静态编排"升级为"LLM 动态决策"**——这正是 Agentic RAG 的本质

> ⚠️ **渐进式提醒**：不要一步到位上完整多 Agent。先把手写 ReAct + 单工具（retrieve）跑通，验证核心质量后，再逐步扩展多工具与反思循环（呼应架构文档 §10.5 的落地建议）。

## 四、动手步骤 📋

1. 写 `tool_registry.py`：定义工具注册器，先注册 `retrieve` 工具
2. 写 `agent.py`：实现手写 ReAct 循环
   - 循环：调模型 → 判断是"调工具"还是"给答案" → 调工具 → 喂结果 → 再调模型
3. 接入 qwen-max 的 Function Calling（把工具描述成 JSON Schema 传给模型）
4. 跑通一个"知识问答 Agent"：用户提问，Agent 自主检索知识库并回答
5. 扩展：再加一个工具（如计算器），验证多工具协同

---

## 五、怎么验证做对了 ✅

1. 问一个需要检索的问题 → 能看到 Agent 的"思考→调 retrieve→观察→回答"完整过程
2. 问一个不需要检索的问题 → Agent 直接答，不调工具（验证它会"判断"）
3. 多工具场景 → Agent 能自己选对工具、正确传参
4. 全程能看到每一步的 Thought/Action/Observation（透明可调试）

## 六、常见坑 ⚠️

1. **死循环**：模型一直调工具停不下来。必须设"最大循环次数"（比如 5 轮），超了就强制结束
2. **工具描述写得不清楚**：模型不知道该不该用、怎么传参。description 和 JSON Schema 要写详细
3. **模型传错参数**：JSON Schema 约束不严，模型传了个错误格式。要做参数校验和容错
4. **上下文越滚越长**：每轮都把历史塞进提示词，几轮后超长。要控制历史长度
5. **🎓 进阶可学（强烈建议，这是 Agent 的高级话题）**：
   - **记忆系统**：短期记忆（对话历史）、长期记忆（向量库 + 摘要）——让 Agent 记住跨会话的信息
   - **多 Agent 协作**：规划者（拆任务）+ 执行者（干活）分工，处理复杂任务
   - 推荐学习：搜"Agent 记忆系统 短期长期记忆""Multi-Agent 协作 规划者执行者"
