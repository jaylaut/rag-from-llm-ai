# P1 · 索引构建开发指引

> **本阶段范围**：不只是"第一次把语料建成向量库"，还包括**索引建完之后怎么跟上语料的变化**（增量更新）。后者是企业级 RAG 与玩具 demo 的分水岭。
>
> 配套决策摘要见《项目架构.md》§十一。

> 📖 **配套文档**：本文中出现的专业名词、指标、数字，均已在 [《P1-索引构建-术语通俗解释》](./P1-索引构建-术语通俗解释.md) 中用"人话"逐个讲清。看到不懂的词，随时回去对照查。

---

## 一、本阶段要做什么

一句话：**把你抓来的各种格式文章（md、html、ipynb、xml/RSS…），变成一份"机器能看懂、能快速搜索、还能持续跟上更新"的档案库。**

打个比方 💡：你要开一座图书馆。P1 干两件事——

1. **建馆**：把每页纸**整理成一张张卡片**，每张卡片写一段内容 + 一个"编号标签"，再按某种规律排好，方便以后"一秒钟找到相关的那张卡"
2. **管馆**：每天有新书入库、有书改版重印、有旧版下架。你需要一套**登记制度 + 更新流程**，而不是每次都把图书馆烧了重建

第 2 件事就是增量更新。它不是"附加功能"，而是索引这个角色的另一半——没有它，你的知识库建完那天就开始"发霉"。

**主线（首次构建，五步）**：

```
原始文件 → ① 解析（提文字） → ② 清洗（去噪/去重/筛选） → ③ 分块（切小段） → ④ 向量化（文字变数字） → ⑤ 入库（存起来能搜）
```

**支线（索引的生命周期，持续运行）**：

```
变更检测 → 变更处理（只重处理差集） → 索引写入（追加 + 软删除） → 对账 → 定期 compaction
```

⚠️ **为什么本阶段必须管这件事**：你的语料全量约 50 万块，按实测 6.6 块/秒算，**全量重建一次约 21 小时**（GPU 时间）。更荒唐的是——你只改了 1 篇文章，却要重嵌整个库。索引生命周期管理就是这个荒谬局面的解法，本节 2.5 会完整展开。

## 二、涉及的技术逐个拆解

### 2.1 文档解析（Document Parsing）

**它是什么**：把你抓来的各种格式文件，提取成"干净、可检索"的纯文本/Markdown。

**先认清我们手里到底有什么**（这是关键，别按"想象"来）：

你的语料不是"PDF + Word"这种办公文档，而是一套**AI 技术语料库**，共 35470 个文件、1.5GB，分 4 类：

| 目录 | 文件数 | 原始格式 | 内容 |
|---|---:|---|---|
| `docs/` | 1552 | HTML | 文档站/教材站（dify、vLLM、d2l…） |
| `github/` | 13926 | md/mdx/ipynb/txt/rst | 94 个开源仓库 |
| `blogs/` | 157 | HTML + XML(RSS) | 6 个科技媒体文章 |
| `kexue/` | 120 | XML(RSS) | 科学空间约 1200 篇技术长文（含 LaTeX 公式） |

**所以真实的解析任务是这些格式**：

| 真实格式 | 怎么解析 | 用到的库 |
|---|---|---|
| `.md/.mdx/.txt/.rst` | 直接读文本（保留 Markdown 结构） | 无（标准库） |
| `.html/.htm` | 多选择器提取正文，去掉导航/广告 | BeautifulSoup + lxml |
| `.xml`（RSS） | 解析 `<content:encoded>` 里的全文，**保护 LaTeX 公式** | 标准库 ElementTree |
| `.ipynb` | 它是 JSON，取 `cells` 里的内容 | 标准库 json |
| `.jsonl` | 元数据文件（标题/URL），不当正文 | 标准库 |
| `.tex` | LaTeX 源码，中文场景价值低，**暂缓** | — |

**原理（人话版）**：这些库本质都是"读文件内部结构 → 定位到文字那一部分 → 抠出来"。

- **HTML** 里文字和排版标签混在一起，BeautifulSoup 帮你找到"正文那块"，剔除"导航/广告/推荐位"这些垃圾
- **ipynb** 本质是个 JSON 文件，`cells` 数组里每个元素是一块内容（markdown 文字 或 代码），要按 `cell_type` 分别取出
- **RSS/XML** 里正文被 `<![CDATA[...]]>` 包着，还可能带 `$...$` 数学公式，提取时不能把公式弄坏

**两个关键决策（已和需求确认）**：

1. **英文内容不要**：github 里混着纯英文仓库。用"中文密度"判断——中文字符占总字符比例低于阈值（如 0.3）的，判定为英文，**过滤掉不入库**（原文件保留不动）。
2. **ipynb 的代码 cell 保留但标记**：代码对"学习"有价值，对"检索问答"价值低。所以**代码块保留下来，但在元数据里标记 `is_code=True`**，检索时对代码块**降权**（或默认不召回，需要时再放开）。

> 📋 这两个决策建议把「解析」和「清洗」拆成两个职责：`parser.py`（格式→文本）+ `cleaner.py`（去噪去重筛选），分开更好测试。

#### 2.1.1 四类素材的解析难点（逐个说清楚）

| 素材 | 难点 | 关键优势（可回溯来源） |
|---|---|---|
| `docs/` HTML | 导航/侧栏/面包屑混正文、SPA靠JS渲染、编码不全 | `index.jsonl` 记录 file→url/title |
| `github/` 仓库 | 中英混杂、ipynb是JSON、目录索引页、fork重复 | `._done` 记录仓库/分支/文件数 |
| `blogs/` 文章 | 正文选择器各家不同、广告推荐污染、JS壳 | `entries.jsonl` 记录标题/URL/时间 |
| `kexue/` RSS | 正文含 LaTeX 公式，转换易弄坏 | 质量最高，值得单独精细处理 |

**一个重要判断** 💡：这份数据的 `README.md` 本身就是"解析难点说明书"，说明这批数据是**专门设计来练解析清洗的**——每个难点都是一道工程题，也是简历里"数据清洗工程能力"的实据。

#### 2.1.2 六步清洗流水线（统一的处理路线）

不管哪类素材，最终都收敛到同一条流水线。这就是模块化 RAG「索引构建」模块的真实实现：

```
① 提取   ② 转文本   ③ 去噪   ④ 去重   ⑤ 筛选   ⑥ 输出
 原始格式 → 纯文本/MD → 去导航广告 → 去重复 → 中文密度/质量 → 标准MD + 元数据
```

| 步骤 | 做什么 | 关键点 |
|---|---|---|
| ① 提取 | 按格式分流（见 2.1 格式表） | md直读、html提正文、ipynb取cells、xml解析RSS |
| ② 转文本 | HTML→Markdown、ipynb→拼接cells | 保留代码块、表格结构；用 markdownify/html2text |
| ③ 去噪 | 删导航/版权/推荐位/广告 | 丢弃"只有链接列表"的目录页；清理垃圾文件 |
| ④ 去重 | 精确（SHA1）+ 近似（SimHash） | 处理 github 的 fork/镜像重复 |
| ⑤ 筛选 | 中文密度、正文长度 | 英文过滤（密度<0.3）、过短(<100字)丢弃 |
| ⑥ 输出 | 统一 Markdown 到 `data/documents/` | 附元数据：来源/路径/站点/标题/URL |

**四个关键设计决策（为什么这么做）**：

1. **保留 Markdown 结构，不压纯文本**——标题层级、代码块、表格本身是结构信息，"按标题切"能提升语义完整性
2. **分块从"固定大小"升级为"按标题层级切"**——这批文档标题结构清晰，先按标题断开再滑窗（详见 2.2）
3. **去重放在入库前**——github 大量 fork/镜像重复，不去重会浪费存储 + 污染检索
4. **LaTeX 单独保护**——kexue 的公式不能粗暴转换，否则乱码

> 💡 **和增量的关系**：第 ④ 步的 SHA1 去重和 2.5.3 的 `content_hash` 是同一套思路——**内容 hash 是整个系统判断"变没变"的统一依据**，构建期用来去重、运行期用来检测变更，一致性成本最低。

**🎓 进阶可学（涉及真实难点的，建议单独研究）**：
- 正文提取算法：`trafilatura`、`readability`、`justext` 这三个库专门做"网页正文抽取"，能自动识别正文区域。手写选择器之外，可以对比它们的效果
- LaTeX 保护：kexue 语料含大量数学公式，如何在清洗/分词时不破坏 `$...$` 片段，是个独立小课题
- 近似去重：SimHash + 汉明距离（README 里已给代码），处理 github 的 fork/镜像重复

### 2.2 分块（Chunking）

**它是什么**：把一整篇长文章，切成一段段"大小合适"的文字块。

**为什么必须切**：三个原因——

1. 文章太长，一次性塞给模型，模型"记不住"也"抓不住重点"
2. 检索的时候，我们想返回的是"最相关的那一小段"，而不是"一整篇万言书"
3. 切得越碎，检索越精准（但要保证每块意思完整）

**一个重要的行业变化（2025–2026）** 💡：过去大家默认"按固定大小切块"（比如每 512 字一刀），但现在业界已经公认这是**过时的默认值**——固定切分会把一个完整意思拦腰斩断。数据研究表明：固定大小分块的"忠实度"只有 0.47~0.51，而"语义/结构分块"能达到 0.79~0.82，**光改分块方式，检索质量就能近乎翻倍**。

**所以本项目的分块策略（按优先级）**：

1. **按标题层级切（首选）**：你的语料大量是 Markdown 教程/笔记，`#`/`##`/`###` 本身就是现成的"语义边界"，先按标题断开——一个 `##` 小节就是一个天然的块
2. **语义边界对齐（次选）**：没有标题的纯文本，优先在段落/句子结束的地方切，别把"因为…所以…"拦腰斩断
3. **固定大小兜底（最后手段）**：只有超长段落才做滑窗硬切（目标 **512 字符、重叠 64 字符**），这不是默认策略，是兜底

**为什么要 64 字重叠** 💡：防止一个完整意思正好被"切在中间"。留 64 字重叠，等于给断口打了个"补丁"。

**父子块（Parent-Child / small-to-big）—— 一个很妙的设计** 🎓：

- 矛盾：检索时希望块**小**（越聚焦越精准），生成时希望块**大**（上下文越完整回答越好）
- 解法：**小块用来检索，大块用来生成**。比如把一个小段落（子块）做嵌入去检索，命中后返回它所属的整个 `##` 章节（父块）给大模型
- 💡 类比：图书馆里，你用"卡片目录"（小卡片）快速找到书，但真正递给读者的是"整本书"（大块）

> 💡 **针对你的真实语料**：这批文档大量是 Markdown 教程/笔记，标题层级（`#`、`##`）本身就是现成的"语义边界"。所以"按标题切 + 父子块"是比纯"段落对齐"更贴合这批数据的做法（对应 2.1.2 的决策 2）。

### 2.2.5 上下文检索（Contextual Retrieval）—— 把切掉的语境补回来 🎓

**它是什么**：切块入库前，让 LLM 看着整篇文档，给**每个块**写一段 50~100 字的"处境说明"（这块属于哪个文档、哪个章节、在讲什么），拼在块前面，再去做嵌入和 BM25 索引。

**为什么需要它** 💡：

- 一个块写着"营收环比增长 3%"，但它被切出来的那一刻，就"忘了"是哪家公司、哪个季度——语义检索和关键词检索都救不回来
- 上下文检索就是让 LLM 在入库时把这层语境补回来：拼上"本文档是 Q2 财报，此块属于营收分析章节"

**效果有多好**（Anthropic 实测，top-20 检索失败率）：

| 方案 | 失败率 | 相对改善 |
|---|---|---|
| 基线（普通嵌入） | 5.7% | — |
| + 上下文嵌入 | 3.7% | -35% |
| + 上下文 BM25 | 2.9% | -49% |
| + 重排 | 1.9% | -67% |

**代价与取舍**：索引时每个块多一次 LLM 调用（离线一次性成本），但换查询时（千万次）的长期收益。**把算力花在入库、换查询时的可靠**，是这两年 RAG 性价比最高的思想转变。

> ⚠️ **本项目建议**：先跑通"按标题切 + 父子块"的基础版本，Contextual Retrieval 作为**可选增强**——等语料稳定、离线索引可控时再上（那时收益最大）。
>
> 💡 **它和增量的关系**：上下文说明是**入库时**用整篇文档算出来的。所以一篇文档改动后，它的每个块都受影响，重建时必须**整篇重算上下文**——这正是 2.5.4 选择"文档级 diff"而非"chunk 级 diff"的重要理由之一。

### 2.3 向量化（Embedding，嵌入）

**它是什么**：把一段文字，变成**一串数字**（一个向量）。这串数字能"代表"这段文字的意思。

**这是整个 RAG 最核心的一步，务必搞懂** 💡：

- 想象把"意思"放到一个多维空间里。意思相近的两句话，在这个空间里**离得近**；意思无关的，**离得远**。
- "苹果手机降价了" 和 "iPhone 打折" → 两个点挨在一起
- "苹果手机降价了" 和 "今天下雨" → 两个点离得老远
- 嵌入模型（embedding model）干的事，就是**把文字换算成这个空间里的坐标**。

**我们用的模型**：`qwen3-embedding:0.6b`，本地 Ollama 部署。

**为什么选它（这是实测出来的，不是拍脑袋）**：

| 对比 | qwen3-embedding:0.6b | bge-m3（你上个项目用的） |
|---|---|---|
| 大小 | 639MB（小） | 1.2GB |
| 速度 | 6.6 条/秒（快） | 0.9 条/秒 |
| 上下文 | 32000 字 | 8000 字 |
| 中文效果 | 更好 | 好 |

核心原因一句话：**你的显卡只有 4GB 显存，这个模型小到能整个塞进显卡里全速跑**，速度比 bge-m3 快 7 倍，效果还更好。

**一个关键细节（指令前缀）** 🎓：
- 这个模型有个特殊能力——你可以在**查询**前加一句指令，告诉它"现在是要做检索"，它就会按检索的方式算向量。
- 比如查询前加 `Instruct: 检索与查询语义相关的内容\nQuery: ...`
- 但**文档**那边不加。这种"查询和文档区别对待"叫**非对称检索**，能提升精度。原理较深，建议单独学习（搜"Qwen3-Embedding instruction-aware 非对称检索"）。

> ⚠️ **和增量的关系**：嵌入模型是**索引的地基**。换模型意味着整个向量空间换了一套坐标系——这是 2.5.8 里"换模型必须全量重嵌"这条红线的来由。

### 2.4 向量入库（存储到 FAISS）

**它是什么**：把上一步算出来的"数字坐标"存起来，并且能快速找出"离查询最近的点"。

**FAISS 是什么**：Meta（Facebook）开源的一个库，专门做"向量检索"——就是"在一堆坐标点里，快速找到离目标点最近的那几个"。

**为什么选 FAISS 而不是 Milvus/Qdrant**（你之前问过，这里用小白话再说一遍）：

- FAISS 是"一个工具库"，像把尺子，import 进来就能用，不占额外资源
- Milvus/Qdrant 是"一套完整系统"，像要单独开一家店，得维护服务、占内存、处理连接
- **你的数据量（几十万块）用 FAISS 绰绰有余，用数据库属于"杀鸡用牛刀"**

**原理（人话版）** 💡：
- 我们用的 `IndexFlatIP` 是"**暴力精确检索**"——就是把查询点和所有存进去的点，**挨个算一遍距离**，取最近的。
- 你可能会问"挨个算不慢吗？"——对几十万到百万级数据，全在内存里算，**毫秒级就出结果**，完全够用。
- 🎓 **进阶可学**：数据到千万级时，FAISS 提供 `IndexIVFFlat`（先粗分桶再细查）和 `IndexHNSW`（图结构跳着查）来加速——原理较深，P1 不用碰。

**还有一路：BM25（关键词检索）** 🎓：
- 除了"按意思搜"（向量），还要一路"按关键词搜"（BM25），两路配合叫**混合检索**。
- BM25 的原理是"统计一个词在文章里出现几次、在全库多罕见"，来给文章打分。这个 P1 也要建，但详细原理放 P2 讲。
- **实现落地**：`bm25.py`（手写，jieba 分词）+ `pipeline.py` 的 `process_document` 在入库时同步构建 BM25 索引（`bm25.add_documents(chunk_texts, ids=chunk_ids)`），并持久化到 `data/index/bm25.json`（`BM25Index.save/load`），P2 检索时直接加载、无需重新分词。

**⚠️ 这里埋着本阶段最大的一个坑** 💡：我们用的 `IndexFlatIP` **不支持单条删除**（FAISS 的 `remove_ids` 只对部分索引类型开放）。也就是说"把一篇文档从库里删掉"这件事，FAISS 本身做不到——怎么办？这是 2.5.5 要解决的问题。

💡 **另一个 FAISS 的关键性质**：`IndexFlatIP` 支持**增量 `add()`**（往里追加新向量，不需要重建），但**不支持 `update` 和删除**。所以本项目的增量策略是：**追加是廉价的，删除和重组要另行设计**。

### 2.5 索引生命周期管理：增量更新（本阶段第二主线）

前面 2.1~2.4 解决"怎么把语料建进索引"。这一节解决**更长期的问题：语料会变，索引怎么跟上**。

#### 2.5.1 为什么必须增量：不这么做会怎样

| 代价 | 说明 | 本项目量级（按实测推算） |
|---|---|---|
| 慢 | 3.5 万文件全量：解析→清洗→切块→嵌入 | 50 万块 ÷ 6.6 块/秒 ≈ **21 小时** |
| 浪费 | 只改了 1 篇文档，却要重嵌整个库 | 0.003% 的变更，撬动 100% 的算力 |
| 脏 | 重建期间新旧索引并存，查询结果不稳定 | 需要额外机制保证查询不中断 |

结论：**必须增量**。但增量不是银弹，它有自己的一致性难题（2.5.7、2.5.8）。

💡 **类比**：全量重建像"把图书馆烧了重排一遍"，增量更新像"图书管理员的登记制度 + 每日更新流程"。前者一晚上烧掉几本书，后者每天花几分钟上架 3 本新书。

#### 2.5.2 企业级方案分级：L1 / L2 / L3 + 一个兜底

| 方案 | 做法 | 时效 | 适用场景 |
|---|---|---|---|
| **L1 定时增量扫描** | cron 比对内容 hash，只 upsert 变更文档 | 分钟~小时 | 制度/手册/Wiki 类文档库 |
| **L2 事件驱动近实时** | Webhook / CDC 捕获变更 → MQ → 消费端处理 | 秒级（2~10s） | 客服知识库、产品文档（**当前企业级主流**） |
| **L3 流式持续摄入** | Kafka 变更流直连处理管线 | 亚秒~秒级 | 行情、日志、客服会话等高频数据 |
| **兜底：蓝绿双索引** | Base 稳定索引 + Delta 增量索引，查询合并，定期 compaction 合并且不停机 | 不停机 | 大规模重建、嵌入模型升级全量重嵌 |

**名词解释** 🎓（三个企业级黑话）：

- **CDC（Change Data Capture，变更数据捕获）**：数据库的"直播流"——任何 insert/update/delete 都实时推出来（代表工具 Debezium），不用轮询
- **Webhook**：文档系统（Confluence、飞书、GitHub）的"订阅通知"——文档一改就回调你的接口
- **MQ（消息队列）**：变更事件的"缓冲区"，削峰填谷 + 失败可重放，是一致性的根基
- **蓝绿双索引**：查询走旧索引（绿），新数据写入新索引（蓝），合并时无缝切换，用户无感知

**选型逻辑**：先按数据源的变更捕获能力选 L1/L2/L3，再按数据规模决定是否叠加蓝绿兜底。

**本项目结论：选 L1** 💡。理由——单机 + 本地文件语料，没有外部系统可订阅，语料变化频率低（学习项目），分钟级延迟完全可接受；引入 MQ、消费端属于杀鸡用牛刀。

⚠️ **但要把流水线的"形"搭对**：即使现在只有 L1，也按「变更检测 → 变更处理 → 索引写入 → 对账」四段组织代码。将来升级到 L2，只是把第一段从 cron 换成 Webhook/CDC，后面三段**原样复用**。这是架构上的便宜事——现在不做，将来就是重构。

#### 2.5.3 核心概念：文档注册表（Document Registry）

增量更新的根基是一张"账本"，记录每个文档的入库状态。**没有账本，"哪些文档需要重处理"这个问题根本无法回答。**

| 字段 | 类型 | 说明 |
|---|---|---|
| `doc_id` | str | 文档唯一标识（用源文件相对路径，稳定且可回溯来源） |
| `content_hash` | str | **清洗后正文**的 SHA1——变更检测的判据 |
| `version` | int | 版本号，每次成功入库 +1（幂等键的一半） |
| `chunk_ids` | list[str] | 本篇切出的所有块 ID（删除/重组时靠它定位） |
| `embedding_model` | str | 入库时用的嵌入模型标识（换模型全量重嵌的依据） |
| `status` | enum | `active` / `deleted` |
| `indexed_at` | datetime | 最近一次成功入库时间（新鲜度加权的数据源） |

**存哪**：`data/index/registry.json`，与 FAISS 索引、BM25 索引同目录。

**为什么用 JSON 不用 SQLite** 💡：零依赖、人眼可读、几千条记录读写是毫秒级。条目到几万条、或需要复杂查询时再换 SQLite——`registry.py` 内部封装，换存储不动上层逻辑。

**`hash_index` 反向索引（服务"按内容判重"）** 💡：

注册表主体是 `doc_id → 记录` 的单向映射，但「新文档入站」（见 2.5.3.1）需要反过来查「这个 content_hash 是不是已经入库过」。所以注册表额外维护一个 `content_hash → doc_id` 的反向索引，随 `registry.json` 一起持久化（可单独存 `hash_index.json`）。

- **为什么需要它**：临时上传的文件，路径每次都可能变（`uploads/tmp_123.md`），用 `doc_id`（相对路径）判重会重复入库；只有按 `content_hash` 才能识别"内容相同"的文档
- **维护时机**：每次 `upsert` 时同步更新反向索引；软删除时不移除（历史 hash 仍需去重，避免已删内容再次入库）

#### 2.5.3.1 增量更新的两类来源（先厘清概念，再谈流水线）

增量更新 = 两个**正交**的入口，二者判据不同、职责不同，不能混为一谈：

| 增量类型 | 触发来源 | 判定方式 | 是否做删除判定 |
|---|---|---|---|
| **A. 存量文档变化** | `raw/` 目录内的文档被修改 / 删除 | 目录 diff（`detect_changes`）：拿 raw/ 全集与注册表比对找差集 | 是（raw 里没了 = 删） |
| **B. 新文档注入** | 用户临时上传 / 某路径下新出现一批文档 | 主动入站（`ingest_new`）：新内容主动来登记，按 `content_hash` 判重 | 否（只增不减） |

**两者的本质区别** 💡：

- 类型 A 是「**拿全集比对找差集**」——前提是 `raw/` 是文档的"真相来源"，任何不在 raw/ 里的文档它都看不见
- 类型 B 是「**新内容主动来报到**」——不依赖 raw/、不受目录位置约束，因为它是"用户塞进来的"而不是"目录里本来就有的"

⚠️ **为什么必须分开**：如果只做类型 A，用户临时上传的文件（不在 raw/ 里）会被 `detect_changes` 完全忽略，甚至更糟——若上传的文件曾被登记过、之后又被移走，会被 A 的"删除判定"误删。类型 B 不触发删除判定，正是为了避免"刚上传的内容被当成该删的"。

#### 2.5.4 四段增量流水线（本地单机版 · 面向类型 A）

```
① 变更检测        ② 变更处理           ③ 索引写入          ④ 对账与收尾
扫描 raw/ →  hash 比对注册表 →  只处理差集 →  向量追加/软删除 →  一致性校验 + 增量报告
```

**① 变更检测（人话版）**：

1. 扫 `raw/` 目录，对每个文件算出 `content_hash`
2. 与注册表比对，差集分三类：**新增**（注册表没有）、**变更**（hash 不同）、**删除**（注册表有、磁盘没了）

⚠️ **为什么必须用 hash 不用 mtime（文件修改时间）**——两个方向都会翻车：

- **假变更**：git checkout、解压、同步工具都会刷新 mtime，"内容没动但时间变了" → 白重嵌一批
- **漏变更**：某些工具改内容却不更新 mtime → 改了但检索不到
- hash 是**内容本身**，骗不了它。且要算**清洗后正文**的 hash——排版变化（改了个空格、重新保存）不算内容变化

**② 变更处理**：

- 新增/变更文档：走 2.1~2.4 的既有链路（解析→清洗→分块→嵌入），产出新 chunk
- 删除文档：不算向量，只需从注册表取出 `chunk_ids`
- 本项目先做**文档级 diff**（hash 变 → 整篇重切重嵌），暂不做 chunk 级 diff

💡 **为什么文档级就够**：单篇文档平均 5~20 块，按实测 6.6 块/秒算，重嵌一篇只要 1~3 秒；而 chunk 级 diff（定位"到底改了哪几段"）要处理块边界漂移，实现复杂度高一个数量级。等单次增量耗时真的成为瓶颈（见 2.5.9 演进路径）再上。

> 🎓 **进阶可学**：chunk 级 diff 的块对齐算法——改动一段后，后续所有块的起始位置都会漂移，如何用最小编辑距离对齐旧块与新块，只重嵌真正变化的块。这是企业级省算力的关键优化。

**③ 索引写入**：

- **FAISS**：新向量 `add()` 追加（`IndexFlatIP` 支持，不需要重建）；旧版本向量走软删除（2.5.5）
- **BM25**：倒排索引本质是"文档清单"，替换对应文档的 entries 即可
- **注册表**：插入/更新记录，`version + 1`
- **父子块关系**：一篇文档重切后，子块 ID 会变，注册表里的旧 `chunk_ids` 必须整体替换（别和新增块混在一起）

**④ 对账与收尾**：

- **一致性校验**：注册表 `active` 文档的 chunk 总数 == FAISS 向量数（未标记删除的）
- **产出增量报告**：新增 X 篇 / 变更 Y 篇 / 删除 Z 篇 / 重嵌 W 块 / 耗时 T 秒
- 报告同时是监控指标和简历素材（见「四、怎么验证做对了」）

#### 2.5.4.5 新文档入站（面向类型 B：上传 / 外部目录注入）

类型 A 的 `detect_changes` 解决不了"用户临时上传、或 raw/ 之外某个目录新冒出一批文档"的情况——因为 A 只扫 `raw/`。类型 B 用**独立的入站入口**处理这类"新来的文档"：

```
入站请求（单个文件路径 / 一批文件 / 字节流）
        ↓
① 算 content_hash
② 查 hash_index：这个内容是否已入库过？
        ├─ 已存在 → 去重，跳过（返回"已存在"）
        └─ 不存在 → ③ 走完整链路：解析 → 清洗 → 分块 → 向量化 → 入库 → 登记
```

**三个关键设计点**：

1. **判重靠 `content_hash` 而不是 `doc_id`**：临时上传的文件路径每次都变（`uploads/tmp_123.md`），用路径判重会重复入库；只有按内容 hash 才能识别"同一份文档"
2. **不做删除判定**：入站只增不减。这避免一个事故——用户上传的文件若曾被登记、之后又被移走，若走类型 A 的"删除判定"会被误删
3. **复用同一套内核**：入站的「解析→清洗→分块→向量化→写入」与类型 A 完全相同，只是**入口**不同（一个是目录 diff 发现，一个是主动登记）。这正是 3.2 里"把 parser/cleaner/splitter/embedder 写成无状态函数"的价值——两套入口共用一套内核

**代码对应**：`ingestor.py`（与 `detector.py` 对称——一个检测存量变化、一个摄入新文档），提供 `ingest_file(path)` 和 `ingest_directory(dir)` 两个入口；批量目录注入复用 2.5.7 的断点续传。

#### 2.5.5 软删除与检索过滤（解决 FAISS 不能删的问题）

回到 2.4 埋的那个坑：FAISS 删不掉单条向量，那怎么"下架一篇文档"？

**做法：软删除（soft delete）**

- 元数据 JSON 每条记录加 `deleted`、`version` 字段
- 检索链路（P2）在召回后、重排前，**过滤掉 `deleted=True` 的块**
- 删除时：注册表 `status` 置为 `deleted` + 对应 chunk 元数据打标 → 逻辑上立刻搜不到

💡 **为什么软删而不是物理删**：增量场景下删除是高频小批量操作，为删 10 条向量重建一次索引（21 小时）完全不划算。软删让删除**"逻辑上立即生效、物理上延迟清理"**——物理清理由 compaction 干（2.5.6）。

⚠️ **这是生产事故高发点**：标记了 `deleted` 但检索链路忘了过滤，用户还能搜到已下架的内容。过滤逻辑必须有测试覆盖（见「四、怎么验证做对了」）。

#### 2.5.6 Compaction（压缩整理）

软删除的代价是索引里堆积"僵尸向量"（查不到的废块），需要定期物理清理：

- **触发条件**（满足其一）：僵尸向量占比 > 10%；距上次 compaction 超过 N 天
- **动作**：按注册表重建索引（只保留 `active` 的 chunk）→ 原子替换索引文件 → 同步刷新元数据映射与注册表

💡 **本项目的甜蜜点**：50 万块、约 2GB 向量，`IndexFlatIP` 重建是**分钟级**——纯内存重组，**不需要重嵌**（向量都还在，只是重新组装）。所以"选 FAISS + 注册表"这个组合，本质上买到的是"**重嵌贵、重组便宜**"这个性质。

⚠️ **两个必须注意的点**：
- **compaction 后 chunk 在 FAISS 里的物理位置（faiss_id）全变了**——元数据 JSON 和注册表的映射必须同步重写，否则对账永远不平
- **重建期间索引不可用**：单机学习场景可接受（停机窗口分钟级）；生产环境用蓝绿双索引兜底——查询走旧索引，重建完原子切换

#### 2.5.7 幂等与断点续传

增量任务可能中途失败（Ollama 挂了、断电、被你 Ctrl+C），恢复后不能把库搞乱：

- **幂等键**：`doc_id + version`。同一文档重复处理，注册表只保留最新版本；重复追加的向量靠 version 标记作废
- **断点续传**：任务开始写 `job.json`（本批处理的文档清单 + 进度），中断后重跑同一批，已完成的跳过
- **失败重试**：单篇失败不阻断整批，记入 dead-letter 列表，批末统一报告

💡 **为什么这对本项目格外重要**：你的全量构建要跑 **21 小时**，不做好断点续传，第 18 小时断电就得从头再来。这是《项目架构.md》9.3 工程化清单里「数据管线：增量索引、断点续传、失败重试」的具体设计。

#### 2.5.8 三个容易想错的问题（架构师视角）

1. **增量更新和检索质量是两件事，要两边配合**。索引更新了，排序逻辑没变，查到的还是老结果。检索侧要配合**新鲜度加权**：`score = 0.7 × 语义相似度 + 0.3 × 新鲜度`，新鲜度按 `indexed_at` 距今天数衰减。权重按领域调——制度类文档"新的大概率是对的"，历史研究类反过来。**改索引是供给侧，改排序是消费侧，两边都要动。**

2. **换嵌入模型 = 全量重嵌，增量救不了你** ⚠️。新旧向量不在同一个语义空间，混在一个索引里检索会"精神分裂"（语义空间错乱的向量互相污染排序）。换模型的标准动作：新模型全量重嵌 → 蓝绿切换 → 旧索引归档。注册表里的 `embedding_model` 字段就是为记录和触发这件事而存在。

3. **删除是"逻辑立即、物理延迟"**。软删除 + compaction 的组合，本质是把**昂贵操作从用户关键路径上挪走**。判断标准：用户要的是"下架的内容马上搜不到"（软删除满足），不是"磁盘上立刻消失"（compaction 满足）。

#### 2.5.9 演进路径（什么时候升级）

| 触发条件 | 升级动作 |
|---|---|
| 单次增量耗时 > 10 分钟 | 上 chunk 级 diff（2.5.4 的进阶优化） |
| 注册表 > 1 万条，JSON 读写变慢 | 换 SQLite（`registry.py` 内部替换，上层不动） |
| 语料来源变成"活的"（接 Confluence/数据库） | L1 → L2：detector 换 Webhook/CDC + MQ |
| 删除频繁，compaction 影响可用性 | 蓝绿双索引（Base + Delta，查询合并） |
| 需要复杂元数据过滤/多租户 | 迁移 Qdrant / LanceDB（`VectorStore` 接口层已隔离，只改实现类） |

#### 2.5.10 和 P7 Agent 的衔接

《项目架构.md》§10.1 说"索引构建 = Agent 的长期记忆写入"。本节的设计让这句话落地：

- 增量更新封装成 Agent 的 `knowledge_update` 工具——Agent 可以自己判断"这个新知识值得入库"
- 注册表的 hash/version 机制，就是 Agent 记忆的"去重与版本管理"
- 增量报告（新增/变更/删除统计）是 Agent 记忆系统的天然审计日志

## 三、动手步骤 📋

### 3.1 源码结构

```
src/rag/ingestion/
├── parser.py       # 格式 → 文本（2.1）
├── cleaner.py      # 去噪 / 去重 / 筛选（2.1.2）
├── splitter.py     # 标题切 + 段落对齐 + 父子块（2.2）
├── embedder.py     # 调 Ollama 向量化（2.3）
├── pipeline.py     # 单文档内核 + 首次全量编排（2.1~2.4）
├── registry.py     # 文档注册表 + hash_index 反向索引（2.5.3）
├── detector.py     # 存量变更检测，面向 raw/ 目录 diff（2.5.4 · 类型 A）
├── ingestor.py     # 新文档入站，面向上传/外部目录（2.5.4.5 · 类型 B）
├── updater.py      # 增量编排：调度 A + B → 处理 → 写入 → 对账（2.5.4）
└── compactor.py    # compaction（2.5.6）
```

> 说明：`detector.py` 与 `ingestor.py` 分别对应增量更新的两类来源（2.5.3.1）——一个检测存量变化（类型 A），一个摄入新文档（类型 B）；`updater.py` 统一调度两者，后段「处理 / 写入 / 对账」复用同一套内核。

⚠️ **开发时的关键决策**：把 parser/cleaner/splitter/embedder 写成**无状态函数**——「一篇文档进，chunk + 向量出」，而不是"遍历目录的批处理脚本"。这样全量和增量才能复用同一套内核（见 3.2）。

### 3.2 开发顺序（重要：不要先写一次性全量脚本）

从左到右五步，按序开发：

| 步骤 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| ① 单文档内核 | parser / cleaner / splitter / embedder 无状态函数化 | 全量与增量的唯一复用点 |
| ② 注册表 + 检测 | `registry.py`（含 hash_index）+ `detector.py`（几百行） | 不依赖全量跑完，此时把 doc_id 规则、哈希点定死 |
| ③ 首次全量 | 直接跑 `updater.py`——注册表为空，所有文档都是「新增」，走的就是增量逻辑 | 先跑 kexue（~1200 篇）验证全链路，再全量 |
| ④ 增量闭环 | 类型 A：增/改/删一篇重跑对账；类型 B：`ingestor.py` 上传/目录注入 | 有了基线，diff 与入站判重对错才有参照物 |
| ⑤ compaction + 监控 | 僵尸清理、对账报告、指标沉淀 | 增量部分才算真正完工 |

💡 **核心原则：全量 = 增量的退化情形**。注册表为空时，所有文档都是"新增"——所以**第一次全量构建不需要单独一套代码，跑的就是增量逻辑**。

💡 **为什么不能反着来**（三条，都很贵）：

- **依赖方向**：增量模块全部消费基线产物（chunk_ids、hash、registry），基线不存在，增量就是空中楼阁
- **验证方向**：没有基线索引，diff 出来该是空还是有货、对账平不平，你没有参照物可判断
- **经济方向**：21 小时嵌入是不可再生的 GPU 成本，先写一次性脚本跑全量，发现结构不对就得重跑——这个代价付不起第二次

### 3.3 动手清单

**首次构建（步骤 ①②③）**：

1. 确认 `raw/raw/` 已解压，语料就位（4 类：docs/github/blogs/kexue）
2. 写 `parser.py`：按格式分发（md/mdx/txt/rst 直读、html 提取正文、ipynb 取 cells、xml 解析 RSS）
3. 写 `cleaner.py`：去噪（去导航/广告/目录页）→ 去重（精确+近似）→ 筛选（中文密度、正文长度）
4. 写 `splitter.py`：实现"按标题切 + 段落对齐 + 512 兜底 + 64 重叠"，并产出**父子块**结构（子块检索、父块生成）
5. 写 `embedder.py`：调用 Ollama 的 `/api/embed` 接口，把文字转成向量
6. 写 `registry.py` + `detector.py`：注册表结构 + hash 比对（此时注册表是空的）
7. 写 `updater.py`：编排「检测 → 处理 → 写入 → 对账」，**全量与增量共用这一个入口**
8. 先跑 `kexue/` 验证全链路，确认索引文件 + 注册表生成正确
9. 再跑全量（21h 量级，挂机 + 断点续传）

> 📋 Contextual Retrieval（上下文说明）作为**可选步骤**先跳过，基础版跑通后再回来加。

**增量部分（步骤 ④⑤）**：

10. 写检索侧的**软删除过滤**（P2 配合，或先在测试脚本里验证）
11. 验证增量闭环（类型 A）：新增 / 修改 / 删除三类各测一遍
12. 写 `ingestor.py`：`ingest_file(path)` + `ingest_directory(dir)`，按 content_hash 判重，验证类型 B 入站（临时上传 + 外部目录批量注入）
13. 写 `compactor.py`：僵尸向量 >10% 触发重组，验证重组后对账能平
14. 沉淀增量报告与三项指标（见「四、可量化指标」）

## 四、怎么验证做对了 ✅

### 4.1 首次构建验证

1. **解析对**：随便丢一个 `kexue/*.xml`，能看到提取出的正文文字（且 LaTeX 公式没乱码）
2. **清洗对**：英文文件被过滤掉，目录索引页被丢弃，重复文件被去重
3. **分块对**：打印几块，每个 `##` 小节是一个块，超长段落被滑窗切分且没把句子/公式拦腰斩断；父子块映射关系正确
4. **向量对**：向量是 1024 维的数字，且"意思相近的两句话"算出来的向量，点积（相似度）明显更高
5. **入库对**：FAISS 索引里的条目数 == 你清洗后分出的块总数 == 注册表里 `active` 的 chunk 总数

### 4.2 增量闭环验证

类型 A（存量文档变化）：

| 验证项 | 做法 | 通过标准 |
|---|---|---|
| **新增生效** | 往 `raw/` 丢一篇新文档，跑增量 | 可检索到该文档内容 |
| **变更生效** | 改一篇已入库文档的一段话，跑增量 | 检索反映新内容，旧内容查不到 |
| **删除生效** | 从 `raw/` 删一篇，跑增量 | 该文档任何 chunk 都召回不了（软删 + 检索过滤都生效） |
| **幂等** | 同一批增量连续跑两次 | 第二次零变更，注册表和索引无重复条目 |
| **对账** | 看增量报告 | active chunk 总数 == FAISS 向量数（未标记删除） |
| **假变更免疫** | `git checkout` 切分支（mtime 全变、内容没变），跑增量 | 差集为空，零重嵌 |

类型 B（新文档入站）：

| 验证项 | 做法 | 通过标准 |
|---|---|---|
| **临时上传新增** | 往 raw/ 之外的任意目录丢一篇新文档，跑 `ingest_file` | 可检索到该文档内容 |
| **外部目录批量注入** | 往某目录丢一批新文档，跑 `ingest_directory` | 全部可检索，无遗漏 |
| **内容去重** | 同一份内容换不同路径/文件名重复入站 | 第二次返回"已存在"，索引无重复向量 |
| **不误删** | 入站后把源文件移走，再跑类型 A 增量 | 入站文档不被判为"删除" |

### 4.3 可量化指标（简历素材）

| 指标 | 含义 | 目标 |
|---|---|---|
| **增量更新延迟** | 文档落盘 → 可检索的耗时 | 单文档 < 10 秒 |
| **重嵌比例** | 变更块数 / 总块数 | 增量 vs 全量，算力节省约 3 个数量级 |
| **对账一致率** | 连续 N 次增量后注册表与索引的一致性 | 100% |

💡 **面试叙事模板**："设计并实现了 RAG 索引的增量更新管线：以内容 hash + 文档注册表做变更检测，文档级 diff 只重处理变更语料，软删除 + 定期 compaction 平衡删除即时性与索引整洁度，增量更新延迟秒级、重嵌算力较全量重建节省约 3 个数量级。"

## 五、常见坑 ⚠️

### 5.1 解析清洗分块向量类

1. **HTML 正文提取不准**：导航/广告/推荐位混进正文。先用"多选择器取最长"策略，必要时对比 trafilatura 等专用库
2. **LaTeX 公式被弄坏**：清洗/分词时 `$...$` 公式容易被破坏。kexue 语料要单独保护公式
3. **编码问题**：Windows 上读文件记得用 `encoding="utf-8"`，否则中文乱码
4. **ipynb 是 JSON**：不能当纯文本直接读，要用 `json.load` 后取 `cells`，且区分 markdown 和 code
5. **一次塞太多文本给 Ollama**：要**分批**（batch）调接口，一次 16 条左右，否则慢或报错
6. **向量没归一化**：算完向量记得做 L2 归一化（让向量长度=1），否则 FAISS 的内积检索不准

### 5.2 增量更新类

7. **用 mtime 做变更检测**：假变更/漏变更双杀，必须用清洗后正文的内容 hash
8. **软删除后检索侧不过滤**：下架内容仍可召回，属生产事故；过滤逻辑要有测试覆盖
9. **compaction 后不刷新映射**：重组后 faiss_id 全变，元数据 JSON 和注册表的映射必须同步重写，否则对账永远不平
10. **换模型后直接增量 upsert**：新旧向量混检污染检索，必须全量重嵌 + 蓝绿切换
11. **增量失败后无幂等重跑**：同一文档向量追加两遍，检索结果重复
12. **先写一次性全量脚本**：将来 `updater.py` 要么重写一遍编排、要么改基线代码——双份逻辑必然漂移

## 六、本阶段完成后要能讲清的原理（学完的检验标准）

对应《项目架构.md》§八 学习清单里 P1 相关的条目。**检验标准：能否不看资料向别人讲清楚一个「为什么」，并举出反例。**

| 模块 | 必须搞懂的原理 | 可验证产出 |

| 数据清洗 | ① 精确去重 vs 近似去重（SimHash 原理）② 中文密度筛选的思路 | 能说清"为什么 fork 镜像会产生大量重复、怎么高效去除" |
| 分块 | ① 固定切分 vs 语义/结构切分的质量差距 ② 父子块为什么能同时满足"检索要小、生成要大" | 用自己的数据实测不同分块策略的召回差异 |
| 嵌入 | ① 为什么归一化后内积 = 余弦相似度 ② 指令前缀与非对称检索 ③ **换模型为何必须全量重嵌** | 能解释"嵌入模型的本质是学一个语义空间映射" |
| 增量更新 | ① 为什么用内容 hash 而不是 mtime ② 软删除 vs compaction 的取舍 ③ 全量为何是增量的退化情形 | 能解释"为什么改 1 篇文档不该重嵌整个库" |
