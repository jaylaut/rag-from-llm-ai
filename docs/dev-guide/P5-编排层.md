# P5 · 编排层开发指引

## 一、本阶段要做什么

一句话：**前面 P1~P4 做的是"零件"，P5 是把零件组装成"可灵活调度、可自由插拔"的流水线，并且能根据不同问题走不同流程。**

这是"模块化 RAG"区别于"朴素/进阶 RAG"的**灵魂**，也是**通往 P7 Agent 的桥梁**。

💡 类比：P1~P4 造好了发动机、轮胎、方向盘。P5 造的是"整车控制台"——能决定"这个场景用几档、走哪条路、要不要开空调"。

```
        ┌────────────── 编排层 Orchestration ──────────────┐
        │   路由 Routing │ 调度 Scheduling │ 知识引导        │
        └──────┬────────────┬────────────┬──────────────────┘
               ↓            ↓            ↓
          (按需调用下面任意模块)
        索引构建   查询预处理   检索   检索后处理   生成
```

---

## 二、涉及的技术逐个拆解

### 2.1 编排层是什么（先建立概念）

**它是什么**：一个"总指挥"，决定"这次请求要按什么顺序、调哪些模块、怎么调"。

**为什么要单独这一层** 💡：朴素 RAG 是"一根直管子"（索引→检索→生成，写死顺序）。但现实问题千变万化：
- 有的问题要"先改写再检索"
- 有的要"检索→发现不够→换个方式再检索"
- 有的要"检索 A 库 → 再用结果去检索 B 库"（多跳）

写死的直管子应付不了这些。编排层就是把这根"管子"变成"可以自由拼的积木"。

---

### 2.2 路由（Routing）

**它是什么**：根据问题特征，决定"走哪条处理路径"。

**P4 已经做了简单版**（按问题类型分流），P5 把它做成**可配置的路由规则**：

```
用户问题
  ├─ 是"知识问答"类 → 走 RAG 检索链路（P2→P3）
  ├─ 是"简单计算"类 → 直接调模型算，不检索
  ├─ 是"总结文档"类 → 直接把整篇文档喂模型
  └─ 是"需要联网"类 → 走搜索工具（P7 引入）
```

**原理**：本质是一个"决策器"。可以先用**规则**（关键词匹配），进阶用**小模型分类**（让模型判断类型）。🎓 更高级的"语义路由"（用向量判断问题属于哪个意图）建议单独学。

### 2.2.5 自适应检索分层（Adaptive RAG）—— 路由的进阶形态 🎓

**核心洞察（2025–2026 业界共识）** 💡：不是所有问题都该走同一条重链路。生产环境约 60~70% 的查询是简单事实问答，如果都走完整的"改写→多轮检索→反思"重链路，会白白烧掉 3~10 倍 token，把延迟从 1~2 秒拖到 4~15 秒。

**解法**：在管线最前面加一个**复杂度分类器**，按难度分流：

| 层级 | 复杂度 | 处理路径 | 占比 |
|---|---|---|---|
| L0 免检索 | 简单常识/计算 | 直接调 LLM 答，不检索 | ~40% |
| L1 单跳检索 | 明确事实问答 | 一次混合检索 + 重排 → 生成 | ~40% |
| L2 多跳/迭代 | 跨文档推理、多步关联 | 多跳检索 / 迭代检索，直到信息充分 | ~15% |
| L3 Agentic | 复杂多工具、多源综合 | 完整 Agent 循环（P7） | ~5% |

**分级收益**：简单查询省掉重链路的延迟与 token，复杂查询才动用高成本能力——用"分层"同时拿到准确率、延迟、成本的最优解。这也是本项目从 RAG 平滑演进到 Agentic RAG 的路线图（详见架构文档 §3.4 / §10.5）。

---

### 2.3 调度（Scheduling）

**它是什么**：控制模块的**执行顺序和次数**。

**几种调度模式（这是本阶段的核心知识）** 🎓：

| 模式 | 含义 | 举例 |
|---|---|---|
| 单次检索 | 搜一次就答 | 普通问答 |
| 多跳检索 | 搜→看结果→再搜（链式） | "A 公司 CEO 是谁，他的母校在哪" |
| 循环/迭代检索 | 搜→生成→不够→再搜，直到满意 | 复杂研究型问题 |
| 分支检索 | 一个问题拆多路，并行搜 | 多角度问题 |

💡 这些模式的本质是"**把检索变成可循环、可分支的流程**"——而这，正是 P7 Agent 的"思考-行动-观察"循环的前身。

---

### 2.3.5 检索质量评估与纠错（CRAG）—— 编排层的"质检员" 🎓

**它是什么**：在"检索"和"生成"之间，加一个**轻量级评估器**，对召回结果打分，判断"检索够不够好"，不够就纠错。

**为什么需要它** 💡：一个常见失效模式是——检索回来的内容不相关，但 LLM 依然"自信地"基于这些无关上下文生成答案（垃圾进垃圾出）。CRAG 就是在这中间设一道"质检"：

```
检索结果 → 评估器打分
  ├─ 正确（Correct）   → 直接进入生成
  ├─ 模糊（Ambiguous） → 保留原结果 + 补充检索
  └─ 错误（Incorrect） → 丢弃，改写查询重试 或 兜底（如拒答/联网）
```

**三种主流纠错范式（进阶可学，建议了解）**：

| 范式 | 思路 | 特点 |
|---|---|---|
| **CRAG**（Corrective RAG） | 检索后加一个评估器，不足则纠正/重试 | 成本低、见效快，**首选**，较基础 RAG 提升约 15–20% |
| **Self-RAG** | 模型自己输出反思标记（需检索？相关？被支撑？） | 全流程自纠错，准确率最高但需专用模型、延迟高 |
| **Adaptive RAG** | 前置分类器按复杂度分流（即 2.2.5） | 与 CRAG 正交，可叠加 |

**为什么先上 CRAG** 💡：它只需在现有管线加一个评估节点（可以用一个轻量 LLM 调用或规则打分），工程复杂度低，效果立竿见影。Self-RAG 需要专用微调模型，工程复杂度和延迟都高，作为更高阶目标。这也呼应了业界共识——"先上 CRAG，不够再上 Self-RAG"。

**关键设计点**：
- **评估器本身要轻**：用一个小模型或规则打分，别为了评估再引入重开销
- **拒答阈值**：评估分数低于阈值时，宁可"拒答/标注信息不足"，也不硬生成——这是治幻觉的最后一道防线

> 这部分与 P7 Agent 无缝衔接：CRAG 的"评估器"在 Agent 语境下就是"工具返回结果的质量判断"——它决定了 Agent 是继续检索、换工具、还是直接回答（见架构文档 §10.5）。

### 2.4 模块化设计的工程价值（这是简历亮点）

**接口抽象**：把每个模块定义成统一接口，比如都实现 `run(input) -> output`。这样：

- 换嵌入模型？改一个类，其余不动
- 换向量库？改一个类（前面文档里反复强调的"接口隔离"）
- 加一个"重排"步骤？往流水线里插一个节点即可

**这就是你 16 年 Java 架构经验最该施展的地方** 💡：Java 里你熟的设计模式（策略模式、责任链、工厂模式），在这里都能用上。比如：
- "不同检索策略" = 策略模式
- "流水线各环节" = 责任链模式
- "按问题类型创建不同管线" = 工厂模式

**把这一层用设计模式的思想组织好，是简历上"工程能力"的有力证明**——它证明了你不只是"调库"，而是"在架构一个系统"。

## 三、动手步骤 📋

1. 定义统一接口：每个模块实现 `run()` 方法，输入输出标准化
2. 实现一个"管线（Pipeline）"类：按配置的步骤顺序执行
3. 实现路由：按问题复杂度分流（L0 免检索 / L1 单跳 / L2 多跳）
4. 实现一个"多跳检索"示例：检索→用结果二次检索
5. 实现一个"检索评估器"（CRAG）：对召回结果打分，不足则改写查询重试或拒答
6. 验证：不同问题能走不同路径，且结果正确

---

## 四、怎么验证做对了 ✅

1. 同一条管线，换掉其中某个模块（比如换个重排算法），其余零改动——验证"解耦"成功
2. 多跳问题（"X 的作者是谁，他写过什么"）能正确链式检索
3. 不同类型问题走不同路径，输出各自正确
4. **CRAG 有效**：故意制造一个"检索不到相关内容"的问题，评估器能识别并拒答/重试，而不是硬生成
5. 代码结构清晰，模块间没有"牵一发动全身"

---

## 五、常见坑 ⚠️

1. **为了抽象而抽象**：模块化别过度。7 个阶段里，真正"可插拔"的是嵌入、检索、重排、生成这几块，别把每个小函数都包装成模块
2. **多跳检索死循环**：循环检索一定要设"最大次数"，否则可能无限搜下去
3. **路由规则越来越多、越来越乱**：及时用设计模式（策略/工厂）收敛，否则后期维护地狱
4. **评估器本身太重**：CRAG 的评估器如果又是重 LLM 调用，会把链路拖慢、成本抬高——用轻量模型或规则打分
5. **🎓 进阶可学**：LangGraph 这类"图编排"工具（把流程画成图）。但要清楚——**本项目手写编排层，就是为了看懂它背后的原理**，而不是直接用现成的
