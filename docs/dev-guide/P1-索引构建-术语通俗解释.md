## 〇 总纲类名词

### 索引（Index）

- **是什么**：把文档处理成"机器能快速搜索"的档案库。包含向量索引（FAISS）+ 关键词索引（BM25）+ 元数据。
- **为什么关心**：P1 整个阶段就是"建索引"+"管索引"。索引建得好不好，直接决定后面检索（P2）的质量上限。
- 💡 类比：图书馆的"卡片目录系统"——书本身在书架上（raw 原始语料），卡片目录（索引）让你一秒找到要找的那张卡。

### 语料（Corpus）

- **是什么**：你手上那批原始文章的总称。本项目是 35470 个文件、1.5GB 的 AI 技术语料。
- **为什么关心**：语料是"原材料"，索引是"加工品"。所有解析、清洗、分块都是围绕语料展开的。

### 增量更新（Incremental Update）

- **是什么**：语料变了之后，只处理"变化的部分"，而不是每次都全量重建。
- **为什么关心**：这是 P1 的第二主线，也是"企业级 RAG"和"玩具 demo"的分水岭。没有它，改 1 篇文章就要重跑 21 小时。
- 💡 类比：全量重建是"把图书馆烧了重排一遍"；增量更新是"每天花几分钟上架 3 本新书、下架 2 本旧书"。

### 无状态函数（Stateless Function）

- **是什么**：一种函数设计——"一篇文档进去，chunk + 向量出来"，不依赖全局状态、不遍历目录。
- **为什么关心**：这是 P1 最关键的设计决策。让"全量构建"和"增量更新"复用同一套内核，避免写两套会漂移的逻辑。
- 💡 类比：无状态函数像"榨汁机"——丢一个橙子进、出一杯汁，跟"之前榨过几个"无关。

### 全量 = 增量的退化情形

- **是什么**：一句很关键的话。意思是——当注册表为空时，所有文档都是"新增"，跑增量逻辑就等于全量构建。所以**不需要单独写一套全量代码**。
- **为什么关心**：这是架构判断的分水岭。面试时能讲清这句，比"我先写了全量又补了增量"高一个段位。

## 一 文档解析名词

### 解析（Parsing）

- **是什么**：把各种格式的文件，提取成"干净、可检索"的纯文本/Markdown。
- **为什么关心**：这是索引构建的第一步。解析质量差，后面全白搭（垃圾进垃圾出）。
- 💡 类比：解析是"把乱糟糟的纸，读成能看懂的正文"。

### Markdown / MD / MDX

- **是什么**：带格式标记的纯文本格式。`#` 是标题、`##` 是二级标题、`` `代码` `` 是代码。MDX 是 Markdown 的增强版（能嵌组件）。
- **为什么关心**：你的语料大量是这种格式，而且标题层级（`#`/`##`）本身就是现成的"语义边界"，后面分块要用到。

### HTML / HTM

- **是什么**：网页格式。文字和排版标签（`<div>`、`<nav>` 等）混在一起。
- **为什么关心**：你的 `docs/` 和 `blogs/` 都是这种格式，需要提取正文、去掉导航/广告。

### BeautifulSoup / lxml

- **是什么**：两个 Python 库，用来解析 HTML/XML。
  - BeautifulSoup：好用的解析器，帮你找到"正文那块"
  - lxml：高性能的底层解析引擎（BeautifulSoup 常拿它当后端）
- **为什么关心**：提取 HTML 正文就靠它们。

### 选择器（Selector）

- **是什么**：一种"定位网页某块内容"的规则，比如"找出 class 是 article-content 的那个 div"。
- **为什么关心**：正文提取就是"用选择器找到正文区块"。不同网站正文所在的标签不同，所以要"多选择器"。

### ipynb（Jupyter Notebook）

- **是什么**：数据科学常用的笔记本格式。本质是个 JSON 文件，里面是 `cells` 数组，每个 cell 要么是 markdown 文字、要么是代码。
- **为什么关心**：你的 github 语料里有 ipynb，不能当纯文本直接读，要用 `json.load` 取 cells。

### cell / cell_type

- **是什么**：ipynb 里的一"块"内容。`cell_type` 区分它是 `markdown`（文字）还是 `code`（代码）。
- **为什么关心**：解析时要按类型分别取出，代码块要打标记降权。

### RSS / XML

- **是什么**：
  - XML：一种结构化数据格式（标签嵌套）
  - RSS：博客/新闻的"订阅源"格式，本质是 XML，用来抓文章
- **为什么关心**：你的 `kexue/` 和 `blogs/` 部分语料是 RSS，正文藏在 `<content:encoded>` 里。

### CDATA

- **是什么**：XML 里的一个特殊标记 `<![CDATA[...]]>`，意思是"这里面的内容别当标签解析，原样保留"。
- **为什么关心**：RSS 的正文（尤其含 `$...$` 公式的）常被 CDATA 包着，提取时要注意。

### LaTeX

- **是什么**：数学公式排版语言，用 `$...$` 或 `$$...$$` 标记公式。
- **为什么关心**：kexue 语料含大量数学公式，清洗/分词时不能把公式弄坏，否则乱码。

### ElementTree

- **是什么**：Python 标准库里的 XML 解析工具。
- **为什么关心**：解析 RSS/XML 用它，零额外依赖。

### 编码（Encoding）

- **是什么**：字符在文件里怎么存成字节。UTF-8 是最通用的中文编码。
- **为什么关心**：Windows 上读文件不指定 `encoding="utf-8"`，中文会乱码。这是经典坑。

### 中文密度

- **是什么**：一段内容里"中文字符占总字符的比例"。
- **为什么关心**：用来判断"这段是不是中文"。低于阈值（如 0.3）判定为英文，过滤掉不入库。
- 💡 类比：中文密度像"盐度计"——测一段水里有多少盐，低于某值就不是海水。

## 二 清洗与去重名词

### 清洗（Cleaning）

- **是什么**：把解析出来的文字"打扫干净"——去噪、去重、筛选。
- **为什么关心**：保证入库质量。噪声和重复会浪费存储 + 污染检索。

### 去噪（Denoise）

- **是什么**：删掉导航、侧栏、面包屑、版权声明、广告、推荐位这些"垃圾"。
- **为什么关心**：这些内容对问答没用，混进正文会降低检索质量。

### 面包屑（Breadcrumb）

- **是什么**：网页顶部那行"首页 > 分类 > 文章标题"的导航路径。
- **为什么关心**：它是典型的"导航垃圾"，提取正文时要剔除。

### 目录页 / 目录索引页

- **是什么**：只有一堆链接列表、没有正文的页面（比如 github 仓库的 README 索引页）。
- **为什么关心**：这种页面对检索没价值，要识别并丢弃。

### 去重（Deduplication）

- **是什么**：删掉重复的内容。分两类：
  - **精确去重**：内容一模一样的重复（用 SHA1 指纹比对）
  - **近似去重**：内容"高度相似"但不完全一样的重复（用 SimHash）
- **为什么关心**：github 的 fork/镜像会产生大量重复，不去重浪费存储 + 污染检索。

### SHA1

- **是什么**：一种"指纹算法"——把一段内容算出一个唯一的 40 位字符串。内容一变，指纹就变。
- **为什么关心**：用来做"精确去重"和"变更检测"。是整个系统判断"内容变没变"的统一依据。

### SimHash（近似去重）

- **是什么**：一种"近似指纹"算法。不要求内容一模一样，只要"高度相似"就能识别为重复。
- **为什么关心**：fork/镜像的重复内容往往不是 100% 一样（可能有细微差异），精确去重抓不到它们，SimHash 能抓。

### 汉明距离（Hamming Distance）

- **是什么**：衡量两个等长二进制串"有几个位置不一样"。
- **为什么关心**：配合 SimHash 用——两个 SimHash 指纹的汉明距离小，说明内容高度相似，判定为近似重复。

### fork / 镜像（fork / mirror）

- **是什么**：
  - fork：github 上"复制别人的仓库到自己账号下"，产生大量重复代码
  - 镜像：某仓库的完整拷贝（可能部署在别的平台）
- **为什么关心**：这是你语料里重复的主要来源，是去重要重点处理的对象。

### 筛选（Filtering）

- **是什么**：按规则丢弃不合格的内容——英文过滤、过短丢弃。
- **为什么关心**：保证入库内容都是"高质量中文正文"。

### 元数据（Metadata）

- **是什么**："关于数据的数据"。比如一篇文档的标题、URL、来源路径、时间。
- **为什么关心**：检索时要做来源回溯（"这句话出自哪篇文档"），靠的就是元数据。

### is_code 标记

- **是什么**：给代码块打的标记（`is_code=True`），表示"这块是代码，不是正文"。
- **为什么关心**：代码对"学习"有价值、对"检索问答"价值低，标记后检索时降权（或默认不召回）。

### markdownify / html2text

- **是什么**：两个把 HTML 转成 Markdown 的工具。
- **为什么关心**：清洗第②步"转文本"时用，把 HTML 正文转成保留结构的 Markdown。

## 三 分块名词

### 分块（Chunking）

- **是什么**：把一整篇长文章切成一段段"大小合适"的文字块（chunk）。
- **为什么必须切**：① 文章太长模型记不住 ② 检索要返回"最相关的一小段"而非"整篇" ③ 切得越碎检索越精准。

### chunk（块）

- **是什么**：分块后的一段文字，是检索的最小单位。
- **为什么关心**：整个 RAG 的检索、重排、生成都围绕 chunk 展开。chunk 划分决定检索质量。

### 固定大小分块（Fixed-size Chunking）

- **是什么**：按固定字数一刀一刀切（比如每 512 字切一段）。
- **为什么不用**：会把完整意思拦腰斩断。📊 固定分块的"忠实度"只有 0.47~0.51。

### 语义分块 / 结构分块（Semantic / Structure-aware Chunking）

- **是什么**：按"语义边界"切——标题层级、段落、句子这些天然的语义单位。
- **为什么用它**：📊 语义/结构分块的忠实度达 0.79~0.82，光改分块方式检索质量就能近乎翻倍。

### 标题层级切分

- **是什么**：按 Markdown 的 `#`/`##`/`###` 标题断开，一个 `##` 小节就是一个块。
- **为什么是首选**：你的语料是 Markdown 教程/笔记，标题本身就是现成的语义边界，最贴合这批数据。

### 滑窗（Sliding Window）

- **是什么**：切长段落时，用"一个窗口往前滑动"的方式切，窗口之间留重叠。
- **为什么关心**：超长段落才用，是"兜底"手段，不是默认策略。

### 重叠（Overlap）

- **是什么**：相邻两个块之间重复的部分（本项目 64 字符）。
- **为什么关心**：防止一个完整意思正好被切在中间。留重叠等于给断口打"补丁"。
- 💡 类比："因为…所以…"这句，如果"因为"在上一块末尾、"所以"在下一块开头，机器就理解断了。留 64 字重叠能接上。

### 父子块（Parent-Child / small-to-big）

- **是什么**：把文档切成"小块"（子块）和"大块"（父块）两层。小块检索、大块生成。
- **为什么关心**：解决"检索要小、生成要大"的矛盾。
- 💡 类比：图书馆用"卡片目录"（小卡片）快速找到书，递给你的是"整本书"（大块）。

### Contextual Retrieval（上下文检索）

- **是什么**：切块入库前，让 LLM 给每个块写一段"处境说明"（这块属于哪个文档、哪个章节），拼在块前面再嵌入。
- **为什么关心**：块被切出来就丢了语境，这段说明把语境补回来。📊 能降 67% 检索失败率（加 BM25 + 重排后）。
- **和增量的关系**：上下文说明是入库时用整篇文档算的，文档一改，所有块都要重算——这是选"文档级 diff"的理由之一。

## 四 向量化与入库名词

### 向量化 / 嵌入（Embedding）

- **是什么**：把一段文字变成一串数字（向量），这串数字能"代表"文字的意思。
- **为什么关心**：RAG 的核心。文字变向量后，才能用"距离近不近"判断"意思近不近"。
- 💡 类比：把"意思"放到多维空间里，"苹果降价"和"iPhone 打折"是相邻两点，"今天下雨"是远处一点。

### 向量（Vector）

- **是什么**：一串数字，比如 1024 个数字。代表一段文字在"语义空间"里的坐标。

### 向量维度（Dimension）

- **是什么**：向量有多少个数字。本项目嵌入是 1024 维。
- **为什么关心**：维度越高表达能力越强，但也越占存储。

### 归一化（Normalization）

- **是什么**：把向量长度缩到 1（L2 归一化）。
- **为什么关心**：归一化后，"内积"就等于"余弦相似度"。FAISS 的 IndexFlatIP 算的是内积，所以必须先归一化。

### 内积 / 余弦相似度

- **内积（Inner Product）**：两个向量逐位相乘再求和。
- **余弦相似度（Cosine Similarity）**：用"两个向量的夹角"衡量相似度。
- **关键关系**：向量都归一化（长度为 1）后，内积 = 余弦相似度。

### 指令前缀（Instruct Prefix）

- **是什么**：qwen3-embedding 的特殊能力——查询侧加一句 `Instruct: ...` 前缀，告诉模型"现在做检索"，精度更高；文档侧不加。
- **为什么关心**：这是"非对称检索"的标准做法，能提升 1~5 个点精度。

### 非对称检索（Asymmetric Retrieval）

- **是什么**：查询和文档"区别对待"——查询加指令前缀、文档不加。
- **为什么关心**：新一代嵌入模型的标志性能力，能提升检索精度。

### Ollama

- **是什么**：本地一键运行大模型的工具。一条命令拉模型、跑模型。
- **为什么关心**：本项目用它本地部署嵌入模型和重排模型。

### batch（批处理）

- **是什么**：把多条文本打包一次发给模型，而不是一条一条发。
- **为什么关心**：一次塞太多会慢或报错，一次 16 条左右最合适。

### FAISS

- **是什么**：Meta 开源的向量检索库，专干"在一堆向量里找最近的那几个"。
- **为什么关心**：本项目用它存向量、做检索。是"向量索引库"（import 即用），不是"向量数据库"（独立服务）。

### IndexFlatIP

- **是什么**：FAISS 里的一种检索算法——暴力精确检索，把所有向量挨个算一遍，取最近的。
- **为什么关心**：数据量小（几十万）时够用，毫秒级出结果。但**不支持单条删除**（这是 P1 最大的坑）。

### IndexIVFFlat / IndexHNSW

- **是什么**：FAISS 里更快的检索算法（倒排索引 / 图结构），数据到千万级才需要。
- **为什么关心**：P1 不用碰，知道"数据大了有升级路径"即可。

### BM25

- **是什么**：经典关键词检索算法。看"词在文档里出现几次、在全库多罕见"打分。
- **为什么关心**：向量检索（按意思搜）+ BM25（按关键词搜）= 混合检索。P1 要建，原理放 P2 讲。

### 混合检索（Hybrid Retrieval）

- **是什么**：向量检索 + BM25 两路配合。
- **为什么关心**：向量懂"意思"但不懂"精确词"，BM25 补短板，二者互补。

### 倒排索引（Inverted Index）

- **是什么**：BM25 的底层数据结构——"词 → 哪些文档含这个词"的映射表。
- **为什么关心**：BM25 更新时，本质是"替换对应文档的条目"，比 FAISS 好处理。

### Milvus / Qdrant

- **是什么**：两个向量数据库（独立服务）。
- **为什么不用**：几十万块数据用 FAISS 绰绰有余，用数据库是"杀鸡用牛刀"。

## 五 增量更新名词

> 这一章对应正文 2.5 节，是 P1 的第二主线，术语最多。

### 变更检测（Change Detection）

- **是什么**：扫描 raw/ 目录，算出每个文件的 hash，和注册表比对，找出"新增/变更/删除"三类差集。
- **为什么关心**：增量更新的第一步。检测准不准，决定后面处理对不对。

### 差集（Diff / 差集三类）

- **是什么**：比对后分三类：
  - **新增**：注册表里没有的
  - **变更**：hash 不同的
  - **删除**：注册表里有、但磁盘上已经没了的
- **为什么关心**：只处理差集，就是"增量"的含义——不碰没变的内容。

### content_hash（内容指纹）

- **是什么**：清洗后正文算出的 SHA1。
- **为什么用它不用 mtime**：
  - mtime（文件修改时间）会"假变更"（git checkout、解压会刷新时间，内容没变）
  - mtime 会"漏变更"（某些工具改内容不更新时间）
  - hash 是内容本身，骗不了它

### 文档级 diff vs chunk 级 diff

- **文档级 diff**：文档一改，整篇重切重嵌（简单，单篇 1~3 秒）。
- **chunk 级 diff**：只重嵌"真正变了的那几块"（省算力，但实现复杂，块边界会漂移）。
- **本项目选文档级**：单篇重嵌才 1~3 秒，chunk 级 diff 复杂度高一个数量级，等真成瓶颈再上。

### 文档注册表（Document Registry）

- **是什么**：一张"账本"（`registry.json`），记录每个文档的入库状态。
- **为什么关心**：没有账本，"哪些文档要重处理"这个问题根本无法回答。

### doc_id

- **是什么**：文档的唯一标识，用源文件的相对路径。
- **为什么关心**：稳定、可回溯来源，是幂等键的一半。

### version（版本号）

- **是什么**：每次成功入库 +1。
- **为什么关心**：幂等键的另一半。配合 doc_id 组成 `doc_id + version`，防止重复处理。

### chunk_ids

- **是什么**：某篇文档切出的所有块的 ID 列表。
- **为什么关心**：删除/重组时靠它定位"这篇文档对应哪些块"。

### embedding_model 字段

- **是什么**：记录入库时用的嵌入模型标识。
- **为什么关心**：换嵌入模型时，靠它触发"全量重嵌"。

### status 字段（active / deleted）

- **是什么**：文档状态——`active`（正常）或 `deleted`（已删除）。
- **为什么关心**：软删除就是靠改这个字段实现"逻辑删除"。

### indexed_at

- **是什么**：最近一次成功入库的时间。
- **为什么关心**：是"新鲜度加权"的数据源（越新的文档越可能对）。

### 软删除（Soft Delete）

- **是什么**：删除时打标记（`deleted=True`），检索时过滤掉，但向量还留在索引里。
- **为什么这么做**：FAISS 删不掉单条向量，为删 10 条重建一次（21 小时）不划算。软删让"删除立即生效、物理延迟清理"。

### 物理删除

- **是什么**：真正从索引里移除向量。
- **为什么关心**：软删只是"逻辑删除"，物理清理要等 compaction。

### 检索侧过滤

- **是什么**：检索链路（P2）在召回后、重排前，过滤掉 `deleted=True` 的块。
- **为什么关心**：这是软删除的"另一半"。⚠️ 只标记不过滤，已下架内容仍能搜到，属生产事故。

### 僵尸向量（Zombie Vector）

- **是什么**：软删除后残留在索引里的"废块"——查不到但占地方。
- **为什么关心**：积累多了浪费内存、拖慢检索，要定期清理。

### Compaction（压缩整理）

- **是什么**：定期把僵尸向量物理清理掉，重建索引。
- **为什么关心**：纯内存重组，分钟级，**不需要重嵌**（向量都还在，只是重新组装）。
- **触发条件**：僵尸向量占比 > 10%，或距上次超过 N 天。

### faiss_id

- **是什么**：chunk 在 FAISS 索引里的"物理位置编号"。
- **为什么关心**：⚠️ compaction 重组后，所有 faiss_id 全变了，元数据和注册表的映射必须同步重写，否则对账永远不平。

### 幂等（Idempotent）

- **是什么**：同一个操作重复执行，结果不变（不会重复插入数据）。
- **为什么关心**：增量任务可能中途失败，重跑时靠幂等键（`doc_id + version`）保证不会重复追加。

### 断点续传（Checkpoint / Resume）

- **是什么**：任务中断后，能从上次进度继续，不用从头再来。
- **为什么关心**：全量构建要跑 21 小时，第 18 小时断电，不做好断点续传就得重来。

### job.json

- **是什么**：记录任务进度的文件（本批处理清单 + 进度）。
- **为什么关心**：断点续传的载体。

### dead-letter 列表

- **是什么**：记录"处理失败的单篇文档"的列表，批末统一报告。
- **为什么关心**：单篇失败不阻断整批，失败的记下来事后处理。

### 对账（Reconciliation）

- **是什么**：一致性校验——注册表里 `active` 文档的 chunk 总数 == FAISS 向量数。
- **为什么关心**：确保"账本"和"实际索引"对得上，防止悄悄出问题。

### 新鲜度加权（Freshness Weighting）

- **是什么**：检索排序时给"新文档"加分：`score = 0.7 × 语义相似度 + 0.3 × 新鲜度`。
- **为什么关心**：制度类文档"新的大概率是对的"，所以要新文档优先。但历史研究类反过来。

### L1 / L2 / L3（增量更新分级）

- **L1 定时增量扫描**：cron 定时比对 hash，只处理变更（分钟~小时级）。**本项目方案**。
- **L2 事件驱动近实时**：Webhook/CDC → MQ → 消费端（秒级）。
- **L3 流式持续摄入**：Kafka 变更流直连（亚秒级）。

### cron

- **是什么**：操作系统的定时任务工具，"每天几点跑一次某个命令"。
- **为什么关心**：L1 方案靠 cron 定时触发增量扫描。

### CDC（Change Data Capture，变更数据捕获）

- **是什么**：数据库的"直播流"——任何增删改都实时推出来，不用轮询。
- **为什么关心**：L2 方案的核心组件。代表工具 Debezium。

### Webhook

- **是什么**：文档系统的"订阅通知"——文档一改就回调你的接口。
- **为什么关心**：L2 方案里捕获变更的方式之一（Confluence、飞书、GitHub 都支持）。

### MQ（消息队列）

- **是什么**：变更事件的"缓冲区"，削峰填谷 + 失败可重放。
- **为什么关心**：L2 方案一致性的根基。本项目现在用不到。

### Kafka

- **是什么**：一种流式消息平台，处理高频数据。
- **为什么关心**：L3 方案的组件。

### 蓝绿双索引（Base + Delta）

- **是什么**：维护两个索引——旧索引（绿，线上用）+ 新索引（蓝，正在更新）。更新完原子切换。
- **为什么关心**：大规模重建、换模型全量重嵌时"不停机"的兜底方案。

### upsert

- **是什么**：update + insert 的合成词——"有就更新，没有就插入"。

### 换模型必须全量重嵌

- **是什么**：换嵌入模型后，新旧向量不在同一语义空间，混检会"精神分裂"（污染排序）。
- **为什么关心**：这是增量更新救不了的红线。标准动作：新模型全量重嵌 → 蓝绿切换 → 旧索引归档。

### knowledge_update 工具

- **是什么**：增量更新封装成 Agent 的工具，Agent 能自己判断"这个新知识值得入库"。
- **为什么关心**：P1 和 P7（Agent）的衔接点。注册表的 hash/version 就是 Agent 记忆的"去重与版本管理"。

### SQLite

- **是什么**：轻量级嵌入式数据库。
- **为什么关心**：注册表条目到几万条、JSON 读写变慢时，换 SQLite（内部替换，上层不动）。

### trafilatura / readability / justext

- **是什么**：三个专门的"网页正文抽取"库，能自动识别正文区域。
- **为什么关心**：手写选择器之外，可以对比它们的效果。

| 数字 | 含义 |

| 毫秒级 | IndexFlatIP 暴力检索几十万块的耗时 |

| 数字 | 含义 |

| 近乎翻倍 | 光改分块方式带来的质量提升 |

### 6.6 Contextual Retrieval 效果数字（Anthropic 实测）

| 方案 | 检索失败率 | 相对改善 |
|---|---|---|
| 基线（普通嵌入） | 5.7% | — |
| + 上下文嵌入 | 3.7% | -35% |
| + 上下文 BM25 | 2.9% | -49% |
| + 重排 | 1.9% | -67% |

📊 **怎么看这张表**：失败率越低越好。从 5.7% 一路降到 1.9%，意味着"搜不到该搜的"的情况减少了三分之二。

### 6.7 增量更新目标指标（简历素材）

| 指标 | 含义 | 目标 |
|---|---|---|
| 增量更新延迟 | 文档落盘 → 可检索的耗时 | 单文档 < 10 秒 |
| 重嵌比例 | 变更块数 / 总块数 | 较全量省约 3 个数量级算力 |
| 对账一致率 | 注册表与索引的一致性 | 100% |

### 6.8 演进触发阈值

| 触发条件 | 升级动作 |
|---|---|
| 单次增量耗时 > 10 分钟 | 上 chunk 级 diff |
| 注册表 > 1 万条 | 换 SQLite |
| 僵尸向量 > 10% | 触发 compaction |
| 语料变"活" | L1 → L2（Webhook/CDC） |
