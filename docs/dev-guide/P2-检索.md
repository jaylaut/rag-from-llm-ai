# P2 · 检索开发指引

## 一、本阶段要做什么

一句话：**用户问一个问题，系统从库里找出"最相关的那几段文字"。**

继续用图书馆的比方 💡：P1 把书整理成了卡片，P2 就是"读者来问问题，管理员快速抽出几张最可能帮到他的卡片"。

这一步是整个 RAG 的**心脏**——检索不准，后面生成再强也是"垃圾进垃圾出"。

```
用户提问 → ① 向量检索（按意思找） + ② BM25检索（按关键词找）
        → ③ 融合两路结果 → ④ 重排（精挑细选） → 输出最相关的几段
```

---

## 二、涉及的技术逐个拆解

### 2.1 稠密检索（向量检索 / Dense Retrieval）

**它是什么**：把问题也转成向量，然后在库里找"坐标离它最近的几段"。P1 已经做了向量入库，这里就是"查询侧"。

**原理** 💡：问题和文档都变成"意思空间"里的点，谁离得近谁相关。"怎么退货"和"售后流程"意思近，向量距离就小，能被找出来——即使字面上没有一个字相同。

**强项**：懂"意思"，能跨同义词匹配。
**盲区**：对"精确词"不敏感，比如错误码 `E5001`、人名"张伟"、代码符号——这些词意思层面"中性"，向量容易判断不准。

---

### 2.2 稀疏检索（BM25 / Sparse Retrieval）

**它是什么**：传统的关键词检索。看问题里的词，在哪些文档里出现了、出现得多不多，据此打分。

**BM25 原理（人话版，三步理解）** 💡：

1. **词频（TF）**：某个词在这篇文章里出现越多，这篇越相关
   - 但有上限——出现 100 次和 50 次差别不大，所以 BM25 做了"饱和处理"（不是线性无限加分）
2. **逆文档频率（IDF）**：这个词越"稀有"，越值钱
   - "的""了"这种词到处都有，不值钱；"区块链"这种词出现少，一旦匹配上，说明真相关
3. **文档长度归一化**：长文章天然词多，不能让它占便宜，要除以文章长度

**强项**：对精确词、专有名词、代码符号敏感。
**盲区**：不懂同义词——"退货"和"售后"字面不同，BM25 就匹配不上。

**为什么用 jieba 分词**：BM25 是英文发明的，英文单词天然有空格分隔。中文没空格，得先用 **jieba** 把句子切成词（"我要退货"→"我/要/退货"），再统计词频。jieba 是中文分词的事实标准，轻量好用。

---

### 2.3 混合检索 + RRF 融合（本阶段的核心知识点）

**它是什么**：把上面的"向量检索"和"BM25 检索"两路结果，合并成一份最终排名。

**为什么要混合**：两路各有所长、各有所短，正好互补——

| | 懂同义词？ | 懂精确词？ |
|---|---|---|
| 向量检索 | ✅ 懂 | ❌ 弱 |
| BM25 | ❌ 不懂 | ✅ 强 |

混在一起，取长补短，召回率（该找到的都找到）显著提升。这也是"进阶 RAG"区别于"朴素 RAG"的关键一步。

**RRF 融合原理（Reciprocal Rank Fusion，倒数排名融合）** 🎓：

- 不直接相加两路的"分数"（因为向量相似度是 0~1，BM25 分数可能是 0~30，量纲不一样，没法直接加）
- 而是看**排名**：每个文档在两路里各排第几名，按 `1/(k+排名)` 给分，再加起来
- 💡 类比：与其纠结"数学考了 95 和语文考了 600 谁更好"，不如直接看"你是全班第 3 名 + 全校第 5 名"，两个名次一综合，谁的综合排名高就是谁
- 好处：**不用调权重**，天生鲁棒。这是业界推荐的融合方法。

---

### 2.4 重排（Rerank）—— 用 cross-encoder，别再用嵌入模型

**它是什么**：召回阶段为了"不漏"，会把范围放宽，可能捞回来 20~50 条（里面有噪声）。重排就是用**更精细的方法**，把这几十条重新精挑细选，留下最准的 3~5 条。

**为什么需要它** 💡：
- 召回阶段追求"宁可多捞，不能漏"——所以返回得宽，噪声多
- 重排阶段追求"精准"——对少量候选精算，把真正相关的顶到最前
- 这叫**"粗召回 + 精排序"**两段式，是工业界通用做法

**一个必须纠正的认知（重要）** ⚠️：

之前的设计是"用嵌入模型对查询+文档分别算相似度来重排"。这其实是 **bi-encoder 的近似方案**，业界已经不用了。真正的生产级重排用的是 **cross-encoder（交叉编码器）**，二者有本质区别：

| | bi-encoder（嵌入模型） | cross-encoder（重排模型） |
|---|---|---|
| 怎么算 | 查询、文档**分别**编码成向量，再比相似度 | 查询、文档**拼在一起**送进模型联合打分 |
| 速度 | 快（文档向量可离线算好） | 慢（每次都要重新算查询+文档对） |
| 精度 | 低（丢了词级交互） | 高（能捕捉细粒度相关信号） |
| 用途 | 海量候选召回 | 少量候选（20~50 条）精排 |

💡 类比：bi-encoder 是"分别给两人拍照，再比照片像不像"；cross-encoder 是"让两人坐一起聊，看聊得投不投机"——后者当然更能判断"配不配"。

**本项目的重排模型**：`Qwen3-Reranker-0.6B`，本地部署（和嵌入模型同属 Qwen3 家族，体积小、显存适配、可本地跑）。

> 🚨 **【2026-10-15 修订】重排部署方案：Ollama 不可用，vLLM 也不可行，最终选 llama.cpp**：
> - **Ollama 不支持重排模型**：实测 `dengcao/Qwen3-Reranker-0.6B:Q8_0` 通过 `/api/chat`、`/api/generate` 均返回无效输出（一串逗号），且 Ollama 无 `/api/rerank` 接口（404）。2026-10 最新资料再次确认"Ollama still has no rerank endpoint"——这是 Ollama 的定位限制（只做 embedding），非版本问题。
> - **vLLM 在本机不可行**：vLLM 官方要求 GPU 计算能力 7.0+（Volta 起，依赖 Triton kernels），本机 GTX 1050 Ti 为 Pascal（compute_cap 6.1）；且 vLLM 不原生支持 Windows。
> - **最终方案：llama.cpp（llama-server）** ✅：支持 Pascal + Windows 官方 release + 官方 GGUF `ggml-org/Qwen3-reranker-0.6B-Q8_0-GGUF` + 标准 `/v1/rerank` 端点。
> - **过渡方案**：llama.cpp 就绪前，用「接口隔离 + 嵌入模型近似重排」占位——定义 `Reranker` 协议，`EmbeddingReranker` 先跑通全链路，后续换 `CrossEncoderReranker`（实现 `/v1/rerank` 调用）上层零改动。

- 用 llama-server 的 `/v1/rerank` 端点传入 `(query, documents)`，取 `relevance_score`，按分数重排
- 为什么选它：① 和嵌入模型同源生态，4GB 显存可共用 ② cross-encoder 精度远高于嵌入近似 ③ 本地部署无 API 费用、隐私可控

**🎓 进阶可学（重要，建议单独学）**：cross-encoder 是 RAG 里"性价比最高的单项优化"——MIT 研究显示两段检索+重排较单段检索精度提升约 40%。推荐搜索："bi-encoder vs cross-encoder RAG 重排"。

## 三、动手步骤 📋

1. 写 `retriever.py`：实现 `dense_search` 和 `sparse_search` 两个方法
2. 实现 RRF 融合函数
3. 写 `reranker.py`：调用本地 `qwen3-reranker` 对融合结果做 cross-encoder 精排，取 top-3
4. 串起来：输入问题 → 输出最相关的 3 段文字
5. （可选）在 reranker 里做**首尾放置**：把最相关的块放最前和最后，次相关的放中间

> 📋 部署 reranker：用 **llama.cpp（llama-server）**，官方 GGUF 一行启动：
> ```bash
> llama-server -hf ggml-org/Qwen3-reranker-0.6B-Q8_0-GGUF:Q8_0 \
>   --embedding --rerank --pooling rank --port 9931
> ```
> （Ollama 不支持重排、vLLM 需 sm_70+ 不适用本机，详见架构文档 §2.4.5。）过渡期用 `EmbeddingReranker` 占位，接口已隔离，llama.cpp 就绪后切换 `CrossEncoderReranker` 即可。

## 四、怎么验证做对了 ✅

1. 构造一个简单测试：库里有 10 段文字，问一个明确的问题，看返回的前 3 段是不是真相关
2. **混合检索比单路好**：故意放一个"只靠关键词能匹配、但向量匹配不到"的文档（或反过来），验证混合检索能捞出来
3. **重排有效**：对比"重排前 top-3"和"重排后 top-3"，看相关文档是否被提到了前面
4. **cross-encoder 比嵌入重排强**（关键验证，也是简历数据）：用同一批查询，对比"嵌入相似度重排"和"cross-encoder 重排"的 Top-3 命中率，后者应明显更高
5. 打印每段的相似度分数，确认排序合理

## 五、常见坑 ⚠️

1. **两路分数直接相加**：量纲不同，加出来没意义。一定要用 RRF（或先各自归一化）
2. **重排对全部候选做**：cross-encoder 慢，如果对海量文档做会极慢。一定是"先粗召回（快）→ 只对 20~50 条候选重排（精）"
3. **用嵌入模型代替 cross-encoder 重排**：精度差一个档次，是已被淘汰的做法，务必用 qwen3-reranker
4. **BM25 没分词就直接统计**：中文必须先用 jieba 分词，否则按整句统计词频没意义
5. **查询侧忘了加指令前缀**：qwen3-embedding 查询侧要加 `Instruct:` 前缀（P1 讲过），否则检索精度下降
6. **最相关的块全堆在中间**：大模型对长上下文有"中间丢失"效应，记得把最相关的内容放首尾
