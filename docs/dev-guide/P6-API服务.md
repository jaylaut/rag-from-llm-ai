# P6 · API 服务开发指引

## 一、本阶段要做什么

一句话：**把前面做好的 RAG 能力，包装成一个"能通过网络访问的服务"，别人（或前端页面）能通过 HTTP 接口调用它。**

到这里，系统才从"一个能跑的脚本"变成"一个真正的产品/服务"。

💡 类比：前面造好了一台能答题的机器。P6 就是给这台机器装上"柜台和窗口"——别人不用钻进机器内部，只要走到窗口，递上问题，就能拿到答案。

---

## 二、涉及的技术逐个拆解

### 2.1 Web API 是什么

**它是什么**：一种"程序对程序"的沟通方式。通过网址（URL）+ 请求方法，让外部程序调用你的功能。

**两个核心概念（小白必懂）**：

- **请求（Request）**：别人发来的一句话，比如"POST /ask，内容是 '怎么退款'"
- **响应（Response）**：你回给他的一句话，比如 `{"answer": "进入订单页点退款…"}`

**常见的请求方法**：`GET`（要数据）、`POST`（提交数据，带请求体）。我们问答用 POST，因为要传问题文本。

---

### 2.2 FastAPI（本项目的框架）

**它是什么**：Python 里一个"写 Web 接口"的框架，特点是**快、简单、自动生成文档**。

**为什么选它**：

1. **自动生成接口文档**：写完代码，访问 `/docs` 就能看到一份可视化的接口文档，还能在线测试——省事且专业
2. **数据校验**：配合 pydantic，自动校验请求参数对不对（比如"问题不能为空"），不用手写一堆 if
3. **异步支持**：能同时处理多个请求，不卡
4. **轻量**：对比 Django（重框架），FastAPI 只做接口，正合适

**🎓 可了解**：FastAPI 底层用的是 ASGI（异步服务器网关接口）标准，Uvicorn 是它的服务器实现。这两个名词了解即可，不必深究。

---

### 2.3 流式输出（Streaming）—— 本阶段的体验加分项

**它是什么**：让回答像 ChatGPT 那样**一个字一个字往外蹦**，而不是干等几秒"啪"地整段出来。

**为什么重要** 💡：
- 大模型生成一句话要几秒，用户干等体验差
- 流式让用户"看着字一个个出来"，心理等待感大幅降低

**原理（人话版）**：模型不是"想完一整段再吐出来"，而是"想一个词吐一个词"。我们把这个过程**实时转发**给用户，而不是等它全部想完。

**实现要点**：请求 QWEN-MAX 时加 `stream: true`，然后逐段读取返回的数据流，转发给前端。

---

### 2.4 日志与监控（体现工程素养，简历亮点）

**它是什么**：记录系统"每次请求干了什么、花了多久、有没有报错"。

**为什么是亮点**：这是"玩具"和"生产级"的分水岭。面试官看到你有日志监控，就知道你不是"跑通就完事"。

**要记什么**：
- 每次问答的耗时（检索多久、重排多久、生成多久）
- 出错时的完整堆栈
- 简单的请求量统计

**用 Python 标准库 `logging` 即可**，不引入额外依赖。

**🎓 进阶可学（RAGOps 可观测性，强烈建议了解）**：业界已经形成"每个回答都能回溯"的标准——用 **OpenTelemetry** 做链路追踪，让每个回答都能追溯"检索了哪些文档 + 用了什么 prompt + 各环节耗时"。这对快速定位"为什么这个回答错了"至关重要，也是企业级 RAG 的标配。

### 2.5 热查询缓存（性能优化，简历亮点）

**它是什么**：把高频查询（比如"怎么退款"这类被反复问的问题）的结果缓存起来，命中就直接返回，不再走完整检索+生成链路。

**为什么有效** 💡：真实场景里，查询分布极度不均——top 5% 的热门问题可能占了很大比例的请求量。缓存这 5%，平均延迟能降约 40%，还能省下重复的 LLM 调用成本。

**实现要点**：用内存缓存（如 `functools.lru_cache` 或简单 dict + TTL）即可起步，进阶可用 Redis。注意缓存键要用"归一化后的查询"（去空格、小写），且语料增量更新后要让相关缓存失效。

## 三、动手步骤 📋

1. 写 `api.py`：用 FastAPI 定义接口
   - `POST /ask`：输入问题，返回答案 + 引用来源
2. 加数据校验：用 pydantic 定义请求体（question 字段必填）
3. 加流式输出：`/ask/stream` 接口，逐字返回
4. 加日志：记录耗时、错误
5. 加热查询缓存：高频查询命中缓存直接返回（注意语料更新后失效）
6. 启动：`uvicorn` 跑起来，浏览器访问 `/docs` 测试

---

## 四、怎么验证做对了 ✅

1. 浏览器打开 `/docs`，能看到接口文档，能在线测试
2. 用 `curl` 或 Postman 发个 POST 请求，能拿到正确 JSON 答案
3. 流式接口能看到"逐字蹦出"的效果
4. 日志文件里能看到每次请求的耗时和结果
5. 故意发个错误请求（空问题），能被优雅拦截并返回错误信息，而不是崩溃
6. 重复问同一个问题，第二次命中缓存、响应明显更快

---

## 五、常见坑 ⚠️

1. **接口没做校验**：空问题、超长问题直接进模型，要么报错要么浪费钱。务必用 pydantic 校验
2. **同步阻塞**：如果不注意，一个慢请求会卡住后面所有请求。用异步或做好并发处理
3. **密钥暴露**：API 里绝不要返回或打印 API Key
4. **日志泄露敏感信息**：日志里不要把用户完整问题、密钥打出来（隐私 + 安全）
5. **🎓 进阶可学**：Docker 容器化（把服务和 Ollama 打包成容器，一键部署）——这是"可部署性"的关键，建议单独学，放工程化收尾时做
