## 〇 总纲类名词

### RAG（Retrieval-Augmented Generation，检索增强生成）

- **是什么**：一种让大模型"先查资料、再回答"的技术。不是直接问模型（它可能瞎编），而是先从你的知识库里**检索**出相关片段，**增强**进提示词，再让模型**生成**答案。
- **为什么关心**：这是整个项目的主题。RAG 治大模型两个病——"幻觉"（瞎编）和"知识过时"。
- 💡 类比：开卷考试 vs 闭卷考试。RAG 就是把闭卷变成开卷——先把参考资料翻出来摆在桌上，再答题。

### 模块化 RAG（Modular RAG）

- **是什么**：RAG 演进的第三代形态。把 RAG 拆成 6 个独立模块（索引、查询预处理、检索、检索后处理、生成、编排），每个模块内部还有可替换的"算子"，通过编排层自由组合。
- **为什么关心**：这是本项目的架构基准。相比前两代（朴素 RAG 是"一根直管子"，进阶 RAG 是"管子加阀门"），模块化 RAG 是"乐高积木"，可插拔、可迭代。
- 💡 类比：朴素 RAG 是固定流水线（只能做一种产品）；模块化 RAG 是模块化工厂（换零件就能做不同产品）。

### 算子（Operator）

- **是什么**：模块内部的一个"具体操作步骤"。比如"重排"就是检索后处理模块里的一个算子。
- 💡 类比：模块是"部门"，算子是部门里的"具体岗位"。部门可换人（换算子），不影响其他部门。

### Agent（智能体）

- **是什么**：能"自主决策、调用工具、多步执行"的大模型应用。和普通对话的区别在于——它不光会"说"，还会"动手"（调工具），会自己规划步骤。
- **为什么关心**：这是项目的终局目标。RAG 做完后，编排层天然能演进出 Agent。
- 💡 类比：普通对话是"图书馆管理员"（你问它答）；Agent 是"私人助理"（你交代"查 X、算 Y、写成报告"，它自己拆步骤、自己动手）。

### trade-off（权衡取舍）

- **是什么**：工程决策的核心思维方式——任何选择都有代价，不是"哪个更好"，而是"在约束下哪个更划算"。
- **为什么关心**：这是架构师和"教程照搬者"的区别。本文档每个选型都写了"为什么选它、为什么不选别的"。

## 一 硬件相关名词

### AVX2 / AVX512

- **是什么**：CPU 的指令集扩展，专门加速向量运算（一次算一堆数）。AVX512 比 AVX2 更强。
- **数字说明**：📊 你的 i7-6700K 有 AVX2、**没有** AVX512。意味着 CPU 跑深度学习慢，重活必须交给 GPU。

### 显存（VRAM）

- **是什么**：显卡上独立的专用内存，模型要跑在显卡上就得装进显存里。
- **数字说明**：📊 你的 GTX 1050 Ti 只有 **4GB 显存**——这是全项目最硬的约束，决定了所有模型选型（只能装 ≤1.5GB 的嵌入模型，因为还要留余量）。

### 4B / 8B / 0.6B

- **是什么**：模型的参数规模。"B" = Billion = 十亿。0.6B = 6 亿参数，4B = 40 亿，8B = 80 亿。
- **为什么关心**：参数越多，模型越"聪明"，但也越占显存。你的 4GB 显存决定了只能选小模型（0.6B）。
- 💡 类比：参数 = 大脑里的"神经元连接数"。0.6B 是"小学生脑子"，8B 是"大学生脑子"——但小学生脑子能塞进你的小书包（4GB 显存），大学生脑子塞不下。

### Ollama

- **是什么**：一个让你在本地电脑上"一键运行大模型"的工具。不用配复杂环境，一条命令就能拉模型、跑模型。
- **为什么关心**：本项目用它本地部署嵌入模型（qwen3-embedding）和重排模型（qwen3-reranker）。
- 💡 类比：Ollama 是"模型界的 Docker"——把"下载模型 + 配置环境 + 跑起来"打包成一条命令。

### GPU 加速 / CPU 回退

- **是什么**：模型推理时优先用显卡（GPU，快），如果显存不够，就退回用 CPU（慢很多）。
- **为什么关心**：你的目标是让模型"全程 GPU 加速、无 CPU 回退"——回退意味着性能崩塌。

### llama-server / nvidia-smi

- **是什么**：`llama-server` 是 Ollama 跑模型时的后台进程；`nvidia-smi` 是查显卡状态的命令（看谁占了多少显存）。
- **为什么关心**：用来验证"模型确实驻留在了显卡上"，是实测证据。

## 二 核心选型名词

### 嵌入（Embedding）/ 嵌入模型

- **是什么**：把一段文字变成一串数字（向量），这串数字能"代表"这段文字的意思。嵌入模型就是干这个转换的模型。
- **为什么关心**：RAG 检索的基础——文字变向量后，才能用"向量距离近不近"来判断"意思近不近"。
- 💡 类比：把"苹果手机降价"翻译成地图上的一个坐标点，"iPhone 打折"这个点会落在它旁边，"今天下雨"则落在老远的地方。

### qwen3-embedding:0.6b

- **是什么**：本项目选的嵌入模型。阿里通义千问（Qwen）家族的第三代嵌入模型，0.6b（6 亿参数）是最小号。
- **为什么选它**：639MB 体积小，能整卡塞进 4GB 显存，实测速度碾压上一个项目用的 bge-m3。

### bge-m3

- **是什么**：智源（BAAI）出的嵌入模型，用户上一个项目用的，本项目用来做对比基准。

### 语义区分度

- **是什么**：衡量嵌入模型"能否把不相关的内容分得够开"的能力。
- **数字说明**：📊 qwen3-embedding 把无关内容的相似度压到 **0.16**，bge-m3 只能压到 **0.32**。数字越小 = 无关内容离得越远 = 排序越干净。

### 大语言模型（LLM）

- **是什么**：就是 ChatGPT、通义千问这类"会聊天、会写文章"的 AI。本质是"超级接话机"——给它一段文字，预测下一句该说什么。
- 💡 类比：一个读过海量书的人，你起个头，它能顺着往下接。

### qwen-max / qwen-plus / qwen-turbo

- **是什么**：通义千问的三个档位。qwen-max 最强最贵，qwen-plus 中等，qwen-turbo 最快最便宜。
- **为什么关心**：本项目用 qwen-max 做生成，但可以降级到 plus/turbo 省钱。

### DashScope / 阿里云百炼

- **是什么**：阿里云的 AI 服务平台，qwen 系列的官方 API 入口。
- **为什么关心**：qwen-max 不是本地跑，是通过这个平台的远程 API 调用。

### OpenAI 兼容接口

- **是什么**：一种业界通行的 API 格式标准（OpenAI 定的）。很多模型服务都提供这种格式，所以"换模型只需改个名字，代码不用动"。
- 💡 类比：像 USB 接口标准——只要都按 USB 做，插谁的设备都能用。

### Function Calling（工具调用/函数调用）

- **是什么**：大模型的一种能力——它不直接回答，而是"说"出"我要调用哪个工具、传什么参数"，由你的程序去执行，再把结果喂回给它。
- **为什么关心**：这是后面做 Agent 的硬前提。没有它，Agent 就没法"动手"。

### FAISS

- **是什么**：Meta（Facebook）开源的向量检索库。专门干一件事——"在一堆向量里，快速找到离目标最近的那几个"。
- **为什么关心**：本项目用它存向量、做检索。
- **重要区分**：FAISS 是"向量**索引库**"（进程内的工具库，import 就能用），不是"向量**数据库**"（独立服务，要单独部署）。二者不是一个层级。

### IndexFlatIP / IndexIVFFlat / IndexHNSW

- **是什么**：FAISS 里不同的"检索算法"：
  - `IndexFlatIP`：暴力精确检索——把所有向量挨个算一遍，取最近的。慢但准。
  - `IndexIVFFlat`：倒排索引——先粗分桶，再在桶里细查。快但略降精度。
  - `IndexHNSW`：图结构检索——像"跳着查"的社交网络，更快。
- **为什么关心**：数据量小（几十万）用 FlatIP 就够；上千万才需要换 IVF/HNSW。

### Milvus / Qdrant / Weaviate / LanceDB

- **是什么**：四个"向量数据库"（独立服务）。它们在 FAISS 之上又包了完整的数据库能力（分布式、权限、元数据过滤、高并发）。
- **为什么不用它们**：本项目的规模（几十万块、单机、单人）用 FAISS 绰绰有余，用数据库是"杀鸡用牛刀"。
- **LanceDB**：介于 FAISS 和 Qdrant 之间的"甜点位"（文件式、零运维），作为后续备选。

### BM25

- **是什么**：一种经典的关键词检索算法。看"问题里的词在哪些文档出现、出现得多不多、这个词稀不稀有"来打分。
- **为什么关心**：向量检索懂"意思"但不懂"精确词"（如错误码 E5001、人名），BM25 补这个短板。
- 💡 类比：向量检索是"按意思搜"，BM25 是"按字面搜"。二者配合 = 混合检索。

### 稠密检索（Dense）vs 稀疏检索（Sparse）

- **是什么**：
  - 稠密检索 = 向量检索（把文字压成密集的向量）
  - 稀疏检索 = BM25（基于词的统计，向量大部分是 0，所以"稀疏"）
- **为什么关心**：二者互补，是混合检索的两条腿。

### RRF（Reciprocal Rank Fusion，倒数排名融合）

- **是什么**：把两路检索结果合并的一种方法。不看"分数"（因为两路分数量纲不同），只看"排名"，按 `1/(k+排名)` 加分再汇总。
- **为什么关心**：不用调权重、天生鲁棒，是混合检索的业界标准融合法。
- 💡 类比：与其纠结"数学 95 分和语文 600 分谁高"，不如看"你是全班第 3 + 全校第 5"，综合排名谁前。

### jieba（结巴分词）

- **是什么**：中文分词工具。把"我要退货"切成"我/要/退货"。
- **为什么关心**：BM25 是英文发明的（英文单词天然有空格），中文没空格，必须先用 jieba 切词。

### 重排（Rerank）

- **是什么**：召回后"精挑细选"的步骤。召回阶段为了不漏会捞回来 20~50 条（含噪声），重排用更精细的方法把最准的 3~5 条顶到最前。
- **为什么关心**：这是 RAG"性价比最高的单项优化"。

### bi-encoder（双塔）vs cross-encoder（交叉编码器）

- **是什么**：
  - bi-encoder：查询和文档**分别**编码成向量，再比相似度。快，适合海量召回。
  - cross-encoder：查询和文档**拼在一起**送进模型联合打分。准但慢，只适合少量候选精排。
- **为什么关心**：这是本项目的关键纠偏——重排必须用 cross-encoder，不能用 bi-encoder（嵌入模型）近似。
- 💡 类比：bi-encoder 是"分别给两人拍照再比像不像"；cross-encoder 是"让两人坐一起聊，看投不投机"。

### Qwen3-Reranker-0.6B（qwen3-reranker）

- **是什么**：本项目选的重排模型（cross-encoder）。和嵌入模型同属 Qwen3 家族，0.6B（6 亿参数）是最小号。
- **为什么选它**：体积小、能本地跑、和嵌入模型同源生态，4GB 显存可共用。
- ⚠️ **Ollama 模型名**：官方 tag `qwen3-reranker` 不存在，社区镜像名是 `dengcao/Qwen3-Reranker-0.6B`（用 `:Q8_0` 量化）。

### Contextual Retrieval（上下文检索）

- **是什么**：Anthropic 提出的技巧——切块入库前，让 LLM 给每个块写一段"处境说明"（这块属于哪个文档、哪个章节），拼在块前面再嵌入。
- **为什么关心**：块被切出来就丢了语境（"营收增长 3%"不知道是哪家公司哪季度），这段说明把语境补回来，实测能降 67% 检索失败率。

### 父子块（Parent-Child / small-to-big）

- **是什么**：把文档切成"小块"和"大块"两层。小块（段落级）用来检索（精准），命中后返回大块（整章）给生成（完整上下文）。
- **为什么关心**：解决"检索要小、生成要大"的矛盾。
- 💡 类比：图书馆用"卡片目录"（小卡片）找书，递给你的是"整本书"（大块）。

### Markdown / HTML / ipynb / RSS / LaTeX

- **是什么**：几种文档格式。
  - Markdown（.md）：带 `#` 标题、代码块的纯文本格式。
  - HTML（.html）：网页格式。
  - ipynb：Jupyter 笔记本（本质是 JSON，里面是代码块和文字块）。
  - RSS（.xml）：订阅源格式，用来抓博客/新闻。
  - LaTeX：数学公式排版语言（`$...$` 里是公式）。
- **为什么关心**：这些是你的真实语料格式，决定了用哪些解析库。

### 中文密度筛选

- **是什么**：判断一段内容"是不是中文"的方法——统计中文字符占总字符的比例，低于阈值（如 0.3）判定为英文，过滤掉不入库。
- **为什么关心**：你的语料里混着大量英文仓库，英文内容对中文问答价值低，要筛掉。

### SimHash（近似去重）

- **是什么**：一种"近似去重"算法。不要求内容一模一样，只要"高度相似"就能识别为重复。
- **为什么关心**：github 的 fork/镜像会产生大量"内容几乎一样"的重复文件，精确去重（SHA1）抓不到它们，SimHash 能抓。

### SHA1 / 内容 hash

- **是什么**：一种"指纹算法"——把一段内容算出一个唯一的短字符串，内容一变，指纹就变。
- **为什么关心**：增量更新时用它判断"文档到底改没改"（详见第六章）。

### 归一化 / 余弦相似度 / 内积

- **是什么**：
  - 归一化：把向量长度缩到 1。
  - 余弦相似度：用"两个向量的夹角"衡量相似度。
  - 内积：两个向量逐位相乘再求和。
  - **关键关系**：向量都归一化（长度为 1）后，"内积"就等于"余弦相似度"。
- **为什么关心**：FAISS 的 IndexFlatIP 算的是内积，所以要先把向量归一化，内积才有意义。

### temperature（温度）

- **是什么**：控制模型"脑洞大小"的旋钮。0 = 死板（只选最可能的词），1 = 天马行空。
- **数字说明**：📊 事实问答设低（0.3 左右），让回答"老实"、少发挥；写诗写小说设高。

### 指令前缀 / Instruct-aware / 非对称检索

- **是什么**：新一代嵌入模型训练时区分了"查询"和"文档"两种角色。查询侧加一句 `Instruct: ...` 前缀能提升精度，文档侧不加。这种"查询文档区别对待"叫非对称检索。
- **为什么关心**：qwen3-embedding 有这个能力，用上能提升 1~5 个点的检索精度。

### Prompt / 提示词 / 提示词工程

- **是什么**：发给模型的"那段话"（含系统指令、参考资料、问题）。提示词工程就是研究"怎么组织这段话让回答最靠谱"。

### 幻觉（Hallucination）

- **是什么**：大模型"一本正经地瞎编"。问它不知道的事，它会编一个看似合理但完全虚构的答案。
- **为什么关心**：RAG 的核心价值之一就是治幻觉——让模型照着资料回答，而不是凭记忆瞎说。

## 三 架构设计名词

### 索引构建（Indexing）

- **是什么**：把原始文档变成"可检索的档案库"的过程（解析→清洗→分块→嵌入→入库）。
- 💡 类比：图书馆把一堆乱纸整理成一张张卡片，按规律排好。

### 查询预处理（Pre-Retrieval）

- **是什么**：检索**之前**，先把用户的问题"翻译/改写/拆解"成更容易搜中的形式。

### 检索（Retrieval）

- **是什么**：拿问题去库里面"找最相关的那几段"。

### 检索后处理（Post-Retrieval）

- **是什么**：检索**之后**的精修——重排、压缩、选择。

### 生成（Generation）

- **是什么**：把检索到的资料 + 问题喂给大模型，生成有依据的回答。

### 编排层（Orchestration）

- **是什么**：RAG 的"总指挥"，决定"这次请求按什么顺序、调哪些模块、怎么调"。
- 💡 类比：整车控制台——决定"这个场景用几档、走哪条路、要不要开空调"。

### 路由（Routing）

- **是什么**：按问题类型/复杂度，分流到不同的处理路径。

### 调度（Scheduling）

- **是什么**：控制模块的执行顺序和次数（单次/多跳/循环/分支）。

### 多跳检索（Multi-hop）

- **是什么**：搜一次 → 用结果再搜一次（链式），解决"答案需要跨文档推理"的问题。
- 💡 类比：查"A 公司 CEO 是谁，他母校在哪"——先查 CEO，再用 CEO 名字查母校。

### 混合检索（Hybrid Retrieval）

- **是什么**：把向量检索（稠密）+ BM25（稀疏）两路结果合并。

### HyDE（假设性文档嵌入）

- **是什么**：查询改写的一种巧妙方法——先让模型**编一段"假想答案"**，拿这段假答案去检索（因为答案和真实文档用词更接近）。
- 💡 类比：问"怎么退款"→ 模型编"申请退款要进订单页、点退款、填原因…"→ 拿这段去搜，能撞上真实文档里的"点击退款"。

### 查询扩展（Query Expansion）

- **是什么**：给问题"加料"——同义扩展（退款→退货→refund）、多查询（一个问题拆成多个角度分别搜）。

### Step-Back Prompting（回退提示）

- **是什么**：让模型先抽象出问题背后的"高层概念"，用更宽泛的问法去检索。
- 💡 类比：问"氢氧化钙在 25℃ 的溶解度"（太具体，原文可能没有）→ 回退成"氢氧化钙的化学性质"（更宽，能搜到）。

### 重排 / 压缩 / 选择

- **重排（Rerank）**：精排候选，见第二章。
- **压缩（Compress）**：去掉上下文里的冗余，省 token。
- **选择（Selection）**：Top-N 截断，控制进入生成的内容量。

### Adaptive RAG（自适应检索分层）

- **是什么**：在管线前加一个"复杂度分类器"，按问题难度分流——简单问题走轻链路，复杂问题才走重链路。
- **为什么关心**：生产环境 60~70% 是简单问题，都走重链路会烧 3~10 倍 token、延迟翻好几倍。
- **四层（L0~L3）**：
  - L0 免检索：简单常识/计算，直接问模型（~40%）
  - L1 单跳检索：明确事实问答，一次检索+重排（~40%）
  - L2 多跳/迭代：跨文档推理（~15%）
  - L3 Agentic：复杂多工具（~5%）

### CRAG（Corrective RAG，纠正式检索）

- **是什么**：在检索和生成之间加一个"检索质量评估器"，对结果打分——正确→生成；模糊→补充检索；错误→丢弃重试或拒答。
- **为什么关心**：防止"检索回来一堆无关内容，模型还自信地瞎编"。先上这个，成本低、见效快（较基础 RAG 提升 15~20%）。

### Self-RAG（自反思检索）

- **是什么**：让模型自己输出反思标记（要不要检索？内容相关吗？答案被证据支撑吗？），全流程自纠错。
- **为什么不是首选**：需要专用微调模型、延迟高，准确率虽最高但工程复杂度大。

### Agentic RAG

- **是什么**：2026 年最大的范式转变——检索不再是固定管线的一步，而是 Agent 自主决策的工具调用。
- **为什么关心**：这是项目终局形态，§3.4 的自适应分层就是通往它的渐进路线。

### 幻觉治理 / 引用溯源（Citation）/ 拒答阈值

- **幻觉治理**：用各种手段让模型"别瞎编"。
- **引用溯源**：让回答标注"这句话出自哪份资料"，可验证。
- **拒答阈值**：检索质量低于某阈值时，宁可说"资料不足"，也不硬编。

### lost-in-the-middle（中间丢失）

- **是什么**：大模型对长上下文有个怪癖——开头和结尾记得牢，**中间**容易忽略。
- **为什么关心**：所以组装上下文时，把最相关的内容放**首尾**，次相关的放中间。

### 父子块层级索引 / 知识图谱

- **父子块层级索引**：把父子块关系存成索引，多粒度召回。
- **知识图谱**：把实体和关系抽成"图"（A 属于 B、B 关联 C），能回答"跨文档关联"问题。本项目标记为"后续"。

### 4.3 检索质量指标（§9.1）

| 指标 | 通俗含义 | 目标值 |
|---|---|---|
| Recall@K（召回率） | Top-K 里"该找的都找到"了吗 | > 0.8 @K=5 |
| Hit Rate（命中率） | 相关文档有没有进 Top-K | > 0.9 |
| MRR（平均倒数排名） | 第一个相关文档排第几 | > 0.7 |
| Faithfulness（忠实度） | 答案有没有忠于资料（没瞎编） | > 0.9 |
| Answer Relevance（答案相关性） | 答案切不切题 | > 0.8 |
| Context Precision（上下文精确度） | 检索到的上下文信噪比 | > 0.8 |

💡 **这些指标怎么理解**：都是 0~1 之间的小数，越大越好。比如 Recall@5 = 0.8，意思是"100 个相关问题里，有 80 个能在前 5 名里找到答案"。

## 五 工程化名词

### RAGOps

- **是什么**：把"运维/DevOps"的理念搬到 RAG 上——用自动化评估、监控、门禁来保障 RAG 系统长期质量。
- 💡 类比：DevOps 管"代码上线"，RAGOps 管"检索质量别退化"。

### Golden Dataset（黄金评测集）

- **是什么**：人工标注的"标准答案集"（50~100 条问题 + 标准答案文档），用来客观评估检索质量。
- **为什么关心**：没有它，"检索质量好不好"就是凭感觉。覆盖四类边界：可回答/歧义/过时文档/应拒答。

### 影子管线（Shadow Pipeline）

- **是什么**：不打断线上服务的"旁路评估"——新构建先在影子管线跑一遍评测集，指标跌破阈值就阻断部署。
- **为什么关心**：把评估做成 CI/CD 门禁，而非事后补课。

### LLM-as-Judge（LLM 当裁判）

- **是什么**：用一个独立的模型（如 qwen-max）给"答案忠实度/相关性"打分。
- **注意**：裁判模型也可能有偏见（judge bias），要用黄金集校准。

### RAGAS / DeepEval

- **是什么**：两个现成的 RAG 评估框架（提供 Faithfulness、Context Precision 等指标的一键评估）。
- **为什么本项目不装**：指标手写更能理解原理；框架留作交叉校验用。

### OpenTelemetry（链路追踪）

- **是什么**：一套"可观测性"标准，能给每个请求打上"链路"，追踪它经过了哪些环节、各花了多久。
- **为什么关心**：让每个回答能回溯到"检索了哪些文档 + 用了什么 prompt"，快速定位坏案例。

### 热查询缓存

- **是什么**：把高频查询的结果缓存起来，命中就直接返回，不再走完整检索+生成。
- **数字说明**：📊 top 5% 的热门查询缓存后，平均延迟能降约 40%。

### p95 / p99

- **是什么**：延迟分位数。p95 = "95% 的请求都低于这个时间"。比平均值更能反映真实体验（平均值会被少数极端值拉高）。

### TTFT（Time To First Token，首 token 延迟）

- **是什么**：从发出请求到"第一个字蹦出来"的时间。
- **为什么关心**：流式输出时，用户最敏感的指标——第一个字快出来，体感就好。

### 容器化 / Docker / docker-compose

- **是什么**：把服务和 Ollama 打包成"容器"，一键部署、环境可复现。

### CI/CD

- **是什么**：持续集成/持续部署——代码改动后自动测试、自动部署的流水线。

### 幂等 / 断点续传

- **幂等**：同一个操作重复执行，结果不变（不会重复插入数据）。
- **断点续传**：任务中断后，重跑能从上次进度继续，不用从头再来。

## 六 增量更新名词

### 文档注册表（Document Registry）

- **是什么**：一张"账本"，记录每个文档的入库状态（doc_id、内容指纹、版本号、状态等）。
- **为什么关心**：增量更新的一切都建立在"有账本"上——知道哪些入库了、哪些变了、哪些删了。

### content_hash（内容指纹）

- **是什么**：清洗后正文算出的 SHA1 指纹。
- **为什么用它判断变更，而不是用 mtime（文件修改时间）**：
  - mtime 会"假变更"（git checkout、解压会刷新 mtime，但内容没变）
  - mtime 会"漏变更"（某些工具改内容却不更新 mtime）
  - hash 是内容本身，骗不了它

### 文档级 diff vs chunk 级 diff

- **文档级 diff**：文档一改，整篇重切重嵌（简单，单篇 1~3 秒）。
- **chunk 级 diff**：只重嵌"真正变了的那几块"（省算力，但实现复杂，块边界会漂移）。

### 软删除（Soft Delete）vs 物理删除

- **软删除**：删除时打标记（`deleted=True`），检索时过滤掉，但向量还留在索引里。
- **物理删除**：真正从索引里移除。
- **为什么软删**：FAISS 的 IndexFlatIP 不支持单条删除，重建又贵。软删让"删除立即生效、物理清理延迟"。

### 僵尸向量 / Compaction

- **僵尸向量**：软删除后残留在索引里的"废块"（查不到但占地方）。
- **Compaction（压缩整理）**：定期把这些僵尸向量物理清理掉，重建索引（纯内存重组，分钟级，不重嵌）。
- **触发条件**：僵尸向量占比 > 10%。

### 幂等键 / job.json

- **幂等键**：`doc_id + version`，保证同一文档重复处理不会重复入库。
- **job.json**：记录任务进度的文件，用于断点续传。

### 蓝绿双索引（Base + Delta）

- **是什么**：维护两个索引——旧索引（绿，线上用）+ 新索引（蓝，正在更新）。更新完原子切换，用户无感知。
- **为什么关心**：大规模重建时不停机的兜底方案。

### CDC / Webhook / MQ / Kafka

- **CDC（Change Data Capture）**：数据库的"变更直播流"——任何增删改都实时推出来。
- **Webhook**：文档系统的"订阅通知"——文档一改就回调你的接口。
- **MQ（消息队列）**：变更事件的"缓冲区"，削峰填谷 + 失败可重放。
- **Kafka**：一种流式消息平台，处理高频数据。
- **为什么关心**：这是 L2/L3 增量更新方案的组件（本项目现在用不到，语料变活才上）。

### L1 / L2 / L3（增量更新分级）

- **L1 定时增量扫描**：cron 定时比对内容 hash，只处理变更文档（分钟~小时级）。**本项目当前方案**。
- **L2 事件驱动近实时**：Webhook/CDC → MQ → 消费端（秒级）。
- **L3 流式持续摄入**：Kafka 变更流直连（亚秒级）。

### upsert

- **是什么**：update + insert 的合成词——"有就更新，没有就插入"。
