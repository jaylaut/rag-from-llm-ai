## 二、核心技术选型

### 2.1 嵌入模型：`qwen3-embedding:0.6b`（本地 Ollama 部署）

**实测对比**（本机 GTX 1050 Ti 实跑数据）：

| 指标 | qwen3-embedding:0.6b | bge-m3（上一项目所用） |
|---|---|---|
| 模型体积 | 639 MB | 1.2 GB |
| 批量吞吐（16 条） | **6.6 条/秒** | 0.9 条/秒 |
| 单查询延迟（热） | **343 ms** | 557 ms |
| 上下文窗口 | **32K** | 8K |
| 中文 MTEB-CN | 66.33 | ≈63 |
| 语义区分度（实测） | 无关项相似度压至 0.16 | 0.32 |
| 许可证 | Apache 2.0 | MIT |

**选择理由**：

1. **显存完美适配**：639 MB 模型可整卡驻留 4 GB 显存，全程 GPU 加速，无 CPU 回退
2. **32K 上下文**：远超 bge-m3 的 8K，长文档切块更从容，减少语义截断损失
3. **指令感知（Instruct-aware）**：查询侧可加指令前缀（如 `Instruct: 检索与查询语义相关的内容\nQuery: ...`），文档侧不加，实现非对称检索，这是新一代嵌入模型的标志性能力
4. **实测语义区分度更好**：无关内容（天气、数据库等）的相似度被压得更低，排序更干净
5. **多语言 + 代码**：覆盖 100+ 语言，为后续学习多语言语料留足空间

**为什么不选更大模型**：4B（2.5 GB）/8B（4.7 GB）MTEB 更高，但 8B 直接撑爆 4 GB 显存，4B 在批量场景下显存吃紧，均不满足"生产级稳定"要求。

**部署方式**：Ollama 本地服务（`http://localhost:11434`），模型已拉取完毕。

### 2.3 向量存储：FAISS（CPU 版）+ JSON 元数据

**选择理由**：

1. **轻量**：单机嵌入，无需部署独立向量数据库服务（对比 Milvus/Qdrant/Weaviate 需要额外进程）
2. **生产级**：Meta 开源，工业界事实标准，`IndexFlatIP` 精确检索（向量已归一化时等价余弦相似度）
3. **可演进**：数据量增长后可平滑切换到 `IndexIVFFlat`（倒排索引）或迁移至 Qdrant，接口层不变

**元数据方案**：JSON 文件与 FAISS 索引一一对应（chunk_id、来源文件、序号），避免引入 SQLite 等额外依赖。

#### 为什么不用 Milvus / Qdrant / Weaviate？

首先要厘清一个概念：**FAISS 是「向量索引库」（进程内嵌入式），Milvus/Qdrant/Weaviate 是「向量数据库」（独立服务）**，二者不是同一层级的竞品。向量数据库内部底层的索引算法（IVF、HNSW）很多就是 FAISS 那一套，它们是在 FAISS 之上又包了一层完整的数据库能力（分布式、元数据过滤、持久化、权限、高并发）。

本项目选择 FAISS 是**基于定位和规模**，而非"配置跑不动"或"它们过时了"——恰恰相反，Milvus/Qdrant/Weaviate 在企业生产环境依然是主流。判断标准如下：

**决策树**（从规模与场景出发）：

```
开始：我需要什么级别的向量存储？
│
├─ 数据量 ≤ 几百万 chunk，单机，学习/个人用
│     → 嵌入式索引库：FAISS / hnswlib
│        （本项目在此分支，选 FAISS）
│
├─ 需要复杂元数据过滤（按字段筛选、混合标量+向量查询）
│     → Qdrant（过滤体验最好）或 Milvus
│
├─ 需要 多用户 / 权限隔离 / 高并发（QPS 上千）
│     → Milvus / Qdrant 集群部署
│
├─ 需要频繁 增量更新 / 删除 / 版本管理
│     → 向量数据库（FAISS 删除需重建索引，是短板）
│
└─ 千万~亿级向量，单机装不下，需分布式
      → Milvus（分布式最强）/ Qdrant
```

**对比表**：

| 维度 | FAISS（本项目） | Qdrant | Milvus | Weaviate |
|---|---|---|---|---|
| 类型 | 嵌入式索引库 | 向量数据库 | 向量数据库 | 向量数据库 |
| 部署形态 | 进程内（import 即用） | 独立服务/嵌入式 | 独立服务/集群 | 独立服务/嵌入式 |
| 适合数据量 | 百万级以内 | 百万~亿级 | 千万~亿级 | 百万~亿级 |
| 元数据过滤 | 无（需自建） | ★ 最强（标量+向量混合查询） | 强 | 强（GraphQL） |
| 增量更新/删除 | 弱（删除需重建） | 强 | 强 | 强 |
| 高并发/多租户 | 不支持 | 支持 | ★ 分布式最强 | 支持 |
| 运维成本 | 零（无进程） | 低 | 中 | 低 |
| 学习价值（手写底层） | ★ 高（可亲手掌控检索细节） | 低（黑盒） | 低 | 低 |

**本项目选 FAISS 的四个理由**：

1. **规模用不到**：抓取文章即使 1 万篇 × 50 块 = 50 万 chunk，向量约 2GB，FAISS `IndexFlatIP` 暴力扫描仍是毫秒级；数据库级的分布式/高并发/过滤能力全部用不上
2. **定位匹配**：本地单机、单人学习，无需多租户、权限、副本
3. **学习价值**：手写底层才能看清"向量怎么存、归一化为什么让内积等价余弦、top-k 怎么算"
4. **资源省心**：嵌入式零进程零运维，不额外占用内存/磁盘，不引入端口连接容错

**演进路径**（触发条件 → 升级方案）：

| 触发条件 | 升级方案 |
|---|---|
| chunk 数超过几百万 | FAISS 换 `IndexIVFFlat` / `IndexHNSW`（仍是 FAISS，仅换索引类型） |
| 需要复杂元数据过滤 | 迁移 Qdrant 或 Milvus |
| 需要多用户/权限/高并发 | Milvus / Qdrant 集群 |
| 频繁增量更新/删除/版本管理 | 向量数据库 |
| 团队多人共用一套库 | 独立向量数据库服务 |

> 接口层已做隔离（`VectorStore` 封装），未来切换只需改一个实现类，上层检索逻辑零改动。
> 补充：中小数据量下还有一个甜点位 **LanceDB**（文件式、零运维、支持 SQL 过滤），介于 FAISS 与 Qdrant 之间，可作为后续备选。
> 增量更新的完整分级方案与本项目落地设计见 §十一 及 [P1-索引构建](dev-guide/P1-索引构建.md) §2.5。

### 2.4.5 重排模型：`Qwen3-Reranker-0.6B`（本地部署）

> **定位纠偏（重要）**：本项目原计划"用嵌入模型做重排"（bi-encoder 近似方案），这是 2025–2026 业界已淘汰的做法。真正的生产级重排必须用 **cross-encoder**（交叉编码器），它是"性价比最高的单项优化"——仅此一项就可让答案质量翻倍（MIT 研究：两段检索+重排较单段检索精度提升约 40%）。
>
> ⚠️ **模型名提示**：Qwen3-Reranker 未发布到 Ollama 官方库，官方 tag `qwen3-reranker` 不存在。社区主流镜像为 `dengcao/Qwen3-Reranker-0.6B`（下载量 2.4 万+）。

> 🚨 **【2026-10-15 修订，重要】重排部署方案：Ollama 不可用 → vLLM 也不可行 → 最终选 llama.cpp**：
>
> **第一层结论（2026-10-14 实测）：Ollama 不支持重排模型**
> - 已拉取的 `dengcao/Qwen3-Reranker-0.6B:Q8_0` 通过 `/api/chat`、`/api/generate` 调用均返回无效输出（一串逗号 `,,,,,,`），无法得到相关性分数；
> - Ollama **没有** `/api/rerank` 接口（返回 404）；
> - 2026-10 最新资料再次证实："Ollama still has no rerank endpoint"——Ollama 官方 API 文档无 rerank 端点、官方库无 rerank 模型（只有用户命名空间镜像）。**这是 Ollama 的定位限制（只做 embedding），不是版本问题**。
>
> **第二层结论（2026-10-15 核查）：vLLM 在本机硬件上不可行** ⚠️
> - 硬件约束：vLLM 官方要求 **GPU 计算能力 7.0+（Volta 架构起）**，其依赖的 Triton kernels 需要 Volta 级硬件；本机 GTX 1050 Ti 是 **Pascal 架构（compute_cap 6.1）**，低于门槛。
> - 系统约束：vLLM 官方文档明确"**不原生支持 Windows**"，需 WSL 或第三方 fork，工程代价大。
> - 因此昨日的"换 vLLM"决策**不成立**，特此修订。
>
> **最终决策：改用 llama.cpp（llama-server）部署 cross-encoder** ✅
> - 完全适配本机：llama.cpp CUDA 后端支持 Pascal 架构，且提供 **Windows 官方预编译 release**；
> - rerank 支持成熟：`llama-server --embedding --rerank --pooling rank` 暴露标准 `/v1/rerank` 端点；
> - 官方 GGUF 已就绪：`ggml-org/Qwen3-reranker-0.6B-Q8_0-GGUF`（Q8_0 约 639MB，4GB 显存轻松跑），无需自己转换；
> - 生态同源：Ollama 本身就基于 llama.cpp，技术栈一致、学习成本低。
>
> **启动命令（一行）**：
> ```bash
> llama-server -hf ggml-org/Qwen3-reranker-0.6B-Q8_0-GGUF:Q8_0 \
>   --embedding --rerank --pooling rank --port 9931
> ```
>
> **过渡方案（不影响 P2~P5 开发进度）**：在 llama.cpp 部署完成前，先用**接口隔离 + 嵌入模型近似重排占位**——定义 `Reranker` 协议，用 `EmbeddingReranker`（bi-encoder 近似）先跑通全链路，llama.cpp 就绪后换成 `CrossEncoderReranker`（实现 `/v1/rerank` 调用即可），上层零改动。这也是 §3.2"接口隔离"思想的直接体现。

**bi-encoder vs cross-encoder 的本质区别**：

| 维度 | bi-encoder（嵌入模型） | cross-encoder（重排模型） |
|---|---|---|
| 编码方式 | 查询、文档**分别**编码成向量，再比相似度 | 查询、文档**拼在一起**送进模型联合打分 |
| 速度 | 快（可离线预计算文档向量） | 慢（每次都要重新算查询+文档对） |
| 精度 | 低（损失了词级交互） | 高（捕捉查询与文档的细粒度交互） |
| 用途 | 海量候选召回（粗排） | 少量候选精排（20~50 条） |

**选择理由**：

1. **同源生态**：与嵌入模型同属 Qwen3 系列，`Qwen3-Reranker-0.6B` 体积小，可在 4GB 显存上与嵌入模型共用本地推理服务（重排是查询时串行调用，不与嵌入批量争抢显存）
2. **效果是质变**：cross-encoder 对"查询+文档"联合打分，能捕捉 bi-encoder 无法表达的细粒度相关信号，是召回后精排的行业标准
3. **本地可部署**：模型文件已就绪（`dengcao/Qwen3-Reranker-0.6B`，0.6B/4B/8B 可选），无需额外付费 API，隐私可控
4. **为学习服务**：亲手对比"用嵌入重排 vs 用 cross-encoder 重排"的 Top-3 命中率差异，正是 §八学习清单里"重排 Rerank"这一项的可验证产出

**部署方式（v3，2026-10-15 修订）**：llama.cpp（llama-server）本地服务，模型用官方 GGUF `ggml-org/Qwen3-reranker-0.6B-Q8_0-GGUF`（后续质量要求提升可换 4B）。重排通过 llama-server 的 `/v1/rerank` 端点传入 `(query, documents)`，取 `relevance_score` 排序。Ollama 不支持重排、vLLM 受本机 Pascal 显卡与 Windows 限制不可行（详见上文核查结论）。

> ⚠️ **显存提示**：4GB 显存同时驻留 `qwen3-embedding:0.6b`（639MB）+ `Qwen3-Reranker-0.6B`（约 639MB）仍绰绰有余；但若升级 reranker 到 4B（约 2.5GB），需评估与嵌入模型的显存叠加，必要时用模型加载/卸载策略串行调用。vLLM 部署 reranker 时同样需关注显存。

### 2.6 分块策略：标题层级切分 + 语义边界 + 父子块（small-to-big）

> **2025–2026 业界共识**：固定大小分块（fixed-size chunking）已被公认为过时默认值。数据研究表明，固定大小分块的忠实度得分仅 0.47–0.51，而语义/层级分块可达 0.79–0.82——**仅改变分块策略就能让检索质量近乎翻倍**，且业界普遍认为 80% 的 RAG 失败可追溯到分块决策。本项目据此从"固定大小"升级为"结构感知分块"。

**核心策略（按优先级）**：

1. **按标题层级切（primary）**：本语料是 Markdown 教程/笔记，`#/##/###` 本身就是现成的语义边界，先按标题断开
2. **语义边界对齐（secondary）**：无标题的纯文本段落，优先在段落/句子边界切，避免拦腰斩断
3. **固定大小兜底（fallback）**：超长段落才做滑窗硬切（目标 512 字符、重叠 64 字符），这是"最后手段"而非默认策略

**父子块（Parent-Child / small-to-big）**：

- **小块精准召回**：小块（如段落级）做嵌入与检索，语义更聚焦，排序更干净
- **大块提供上下文**：命中后返回其父块（如整个 `##` 章节），给生成阶段完整上下文
- **选择理由**：解决"检索粒度 vs 生成上下文"的经典矛盾——检索要小、生成要大

**Contextual Retrieval（上下文检索，Anthropic 2024）**：

- 切块入库前，让 LLM 看着整篇文档，给每个块写一段 50–100 token 的"处境说明"（该块属于哪个文档、哪个章节、讲什么），拼在块前面再嵌入
- **为什么有效**：块被切出来那一刻就丢失了"哪家公司/哪个季度/哪个章节"的语境，语义检索和关键词检索都救不回来；这段前置说明把切掉的语义补回来
- **实测数据**（Anthropic 基准，top-20 检索失败率）：基线 5.7% → 加上下文嵌入 3.7%（-35%）→ 加 BM25 2.9%（-49%）→ 加重排 1.9%（-67%）
- **取舍**：索引时多一次 LLM 调用（离线一次性成本，可配 Prompt Cache 压到约 $1/M token），换取查询时（千万次）的长期收益——把算力花在入库，是这两年 RAG 性价比最高的思想转变
- **本项目落地**：作为 P1 索引构建的可选增强算子（语料稳定、离线索引可控时收益最大），与"按标题切"天然互补——标题切保住粗粒度结构，上下文说明补回细粒度语境

## 三、模块化 RAG 架构设计

### 3.1 为什么是模块化 RAG（而不是朴素/进阶 RAG）

参考《RAG 检索增强生成架构演进：朴素 → 进阶 → 模块化》，三代架构的本质区别：

| 代际 | 流程 | 局限 |
|---|---|---|
| 朴素 RAG | 索引 → 检索 → 生成（线性管道） | 检索质量差、无后处理、噪声直接进生成 |
| 进阶 RAG | 检索前处理 + 检索后处理（重排/过滤） | 仍是固定管道，灵活性不足 |
| **模块化 RAG** | **模块 Module → 子模块 Sub-module → 算子 Operator，可自由编排** | 全局可控、可迭代、可插拔 |

模块化 RAG 的核心思想：**把 RAG 拆成 6 大功能模块，每个模块内含可替换的算子，通过编排层（Orchestration）组合成不同范式**。这也是后续开发 Agent 的天然基础——Agent 本质上就是对 RAG 模块的动态编排。

### 3.2 六大模块设计

```
┌─────────────────────────────────────────────────────────────────┐
│                    ⑤ 编排层 Orchestration（中枢）                 │
│         路由 Routing │ 调度 Scheduling │ 知识引导 Knowledge Guide  │
└──────┬──────────┬──────────┬──────────┬──────────┬──────────────┘
       │          │          │          │          │
  ①索引构建   ②查询预处理  ③检索      ④检索后处理   ⑥生成
  Indexing    Pre-Retrieval Retrieval  Post-Retrieval Generation
```

#### ① 索引构建（Indexing）

| 算子 | 本项目实现 | 技术原理 |
|---|---|---|
| 解析 Parsing | 多格式解析（md/html/ipynb/xml/RSS），保留 Markdown 结构 | 按格式分流，提取正文 |
| 清洗 Cleaning | 去噪（去导航/广告/目录页）+ 去重（精确+SimHash 近似）+ 中文密度筛选 | 保证入库质量，减少冗余与噪声 |
| 分块 Chunking | 按标题层级切 + 语义边界对齐 + 512 兜底 + 64 重叠 | 结构感知分块，忠实度较固定切分近乎翻倍 |
| 优化 Optimization | Contextual Retrieval（LLM 写上下文说明）/ small-to-big 父子块 | 补回切块丢失的语境；小块召回、大块生成 |
| 结构组织 | 层级索引（父块-子块）、知识图谱（后续） | 多粒度召回提升上限 |

> 详细说明见 [P1-索引构建](dev-guide/P1-索引构建.md)（含四类语料难点、六步清洗流水线、设计决策）。

#### ② 查询预处理（Pre-Retrieval）

| 算子 | 本项目实现 | 技术原理 |
|---|---|---|
| 查询转换 Query Transform | 改写（HyDE）、子查询分解 | 用 LLM 把模糊问题改写成可检索形式 |
| 查询扩展 Query Expansion | 同义扩展、多查询召回 | 提升召回率 |
| 路由 Routing | 按问题类型选择检索通道 | 不同问题走不同最优路径 |

#### ③ 检索（Retrieval）

| 算子 | 本项目实现 | 技术原理 |
|---|---|---|
| 检索器 | qwen3-embedding（稠密）+ BM25（稀疏） | 语义 + 关键词互补 |
| 融合 | RRF 倒数排名融合 | 无需调参的鲁棒融合 |
| 检索源 | 本地 FAISS（后续可加远程/图检索） | 混合源 Hybrid Retrieval |

#### ④ 检索后处理（Post-Retrieval）

| 算子 | 本项目实现 | 技术原理 |
|---|---|---|
| 重排 Rerank | 本地 cross-encoder（Qwen3-Reranker，llama.cpp 部署，详见 §2.4.5） | 粗召回后精排，Top-N 精准度大幅提升 |
| 压缩 Compress | 上下文压缩（去冗余）、LLM 压缩 | 减少噪声，节省 token |
| 选择 Selection | Top-N 截断 + lost-in-the-middle 缓解（首尾放置） | 控制上下文量，避免"中间丢失" |

#### ⑤ 编排（Orchestration）—— 模块化 RAG 的"大脑"

| 算子 | 说明 |
|---|---|
| 路由 Routing | 按查询复杂度分流到不同检索路径（Adaptive RAG，见 §3.4） |
| 调度 Scheduling | 控制模块执行顺序（单次/多跳/循环/分支检索） |
| 知识引导 Knowledge Guide | 利用结构化知识指导检索与生成 |
| 检索评估 Grader | 评估检索结果质量，不足则纠正/重试（CRAG，见 §3.4） |

#### ⑥ 生成（Generation）

| 算子 | 本项目实现 | 技术原理 |
|---|---|---|
| 生成微调 | 提示词工程（严格基于资料、引用来源） | 约束幻觉 |
| 验证 Verification | 引用溯源、答案-资料一致性校验、拒答阈值 | 可信度保障 |

### 3.4 自适应检索分层（Adaptive RAG）—— 编排层的关键升级

> 2025–2026 业界共识：**不是所有问题都该走同一条重链路**。生产环境约 60–70% 的查询是简单事实问答，若都走完整 Agentic 多轮循环，会白白烧掉 3~10 倍 token、把 p95 延迟从 1~2 秒拖到 4~15 秒。自适应 RAG 在管线前加一个**复杂度分类器**，按难度分流——这是混合负载下的标准架构决策。

| 层级 | 复杂度 | 处理路径 | 占比 |
|---|---|---|---|
| L0 免检索 | 简单常识/计算 | 直接调 LLM 答，不检索 | ~40% |
| L1 单跳检索 | 明确事实问答 | 一次混合检索 + 重排 → 生成 | ~40% |
| L2 多跳/迭代 | 跨文档推理、多步关联 | 多跳检索 / 迭代检索，直到信息充分 | ~15% |
| L3 Agentic | 复杂多工具、多源综合 | 完整 Agent 循环（规划→检索→评估→反思） | ~5% |

**分级收益**：简单查询省掉重链路的延迟与 token；复杂查询才动用高成本的 Agentic 能力——用"分层"同时拿到准确率、延迟、成本三者的最优解。

**两个现代纠错范式（编排层的核心进阶）**：

- **CRAG（Corrective RAG，纠正式检索）**：在检索与生成之间加一个**轻量级检索评估器**，对召回结果打分——`正确`→直接生成；`模糊`→保留原结果并补充检索；`错误`→丢弃、改写查询重试或兜底。防止"LLM 基于无关上下文自信地瞎编"这一常见失效。**先上 CRAG**（在现有管线加一个评估节点，成本低、效果明显，较基础 RAG 提升约 15–20%）。
- **Self-RAG（自反思检索）**：让模型输出反思标记（需检索？内容相关？答案被证据支撑？），全流程自纠错，准确率最高但需专用微调模型、延迟高。作为更高阶目标，非首选。

> **选型建议**：先上 CRAG（成本低、见效快），准确率仍不足时再考虑 Self-RAG。这与本项目"手写底层、循序渐进"的定位一致。

### 3.3 数据流

```
离线索引：
原始文档(raw) → 解析(多格式提正文) → 清洗(去噪/去重/中文筛选)
             → 分块(按标题切 + 语义边界) → [可选]上下文说明(Contextual Retrieval)
             → [嵌入(qwen3-embedding) → FAISS]  + 父子块层级结构
               [分词(jieba)           → BM25]

在线问答：
用户提问 → 查询预处理(指令前缀/改写) → 路由(复杂度分流，见§3.4)
        → 混合检索(FAISS稠密 + BM25稀疏) → RRF融合
        → 重排(Qwen3-Reranker cross-encoder，llama.cpp 部署) → Top-N 上下文(首尾放置)
        → [热查询缓存命中则直接返回]
        → Prompt组装(系统提示 + 引用资料 + 问题)
        → QWEN-MAX 远程生成 → 引用溯源校验 → 带引用来源的回答
        → 影子管线评估(忠实度/相关性) + 链路追踪埋点

增量更新（索引建完之后的生命周期管理，详见 §十一）：
变更检测(raw扫描 + 内容hash比对注册表) → 文档级diff(只重处理差集)
        → FAISS追加 + 软删除 → 对账(注册表↔索引) → 定期compaction
```

## 七、关键技术原理速查

### 为什么混合检索优于单一检索？

- **稠密向量**：擅长语义相似（"怎么退货" ≈ "售后流程"），但对精确词（错误码、人名）不敏感
- **BM25 稀疏**：擅长词面匹配（专有名词、代码），但不理解同义改写
- **RRF 融合**：`score = Σ 1/(k + rank)`，只看排名不看分数分布，无需归一化调参

### 为什么查询要加指令前缀（Qwen3-Embedding 特有）？

新一代指令感知嵌入模型训练时区分了"查询"和"文档"两种角色。查询侧加 `Instruct: ...` 前缀能显著提升检索精度（官方 ablation 约 1-5 个点），文档侧不加。这是非对称检索（asymmetric retrieval）的标准做法。

### 为什么重排是性价比最高的一环？

召回阶段追求高召回率（宁可多不可漏）， inevitably 引入噪声；重排阶段用更精细的模型（**cross-encoder，非 bi-encoder**）对少量候选（20-50 条）精算相关性，以很小的开销换取最终 Top-3/5 的精准度大幅提升。这是进阶 RAG 最重要的单项优化，MIT 研究显示两段检索+重排较单段检索精度提升约 40%。

### 为什么 cross-encoder 重排优于"用嵌入模型重排"？

bi-encoder（嵌入模型）把查询和文档**分别**编码成向量再比相似度，丢失了词级的细粒度交互；cross-encoder 把查询和文档**拼接**后联合打分，能捕捉"这个词在这个语境下是否相关"的交叉信号。代价是慢（无法离线预计算），所以只对少量候选做——这正是"粗召回（快）+ 精排序（准）"两段式设计的由来。

### 为什么要做上下文检索（Contextual Retrieval）？

分块是"有损"操作——一个块写着"营收环比增长 3%"，但被切出来那一刻就不知道"哪家公司、哪个季度"了，语义检索和关键词检索都救不回来。上下文检索让 LLM 在入库时给每个块补一段"处境说明"，把切掉的语义补回来，实测可降低约 35%（嵌入）/ 67%（加 BM25 + 重排）的检索失败率。

### 为什么要把最相关的内容放首尾（lost-in-the-middle）？

大模型对长上下文存在"中间丢失"效应——对开头和结尾的内容记得牢，对中间的内容容易忽略。因此重排后组装上下文时，把最相关的块放在最前和最后、次相关的放中间，能有效缓解这一效应，提升生成质量。

|---|---|---|
| 数据清洗 Cleaning | ① 精确去重 vs 近似去重（SimHash 原理）② 中文密度筛选的思路 | 能说清"为什么 fork 镜像会产生大量重复、怎么高效去除" |
| 嵌入 Embedding | ① 为什么归一化后内积=余弦相似度 ② 为什么查询/文档要非对称（指令前缀）③ 向量维度、MRL 截断的取舍 | 能解释"嵌入模型的本质是学一个语义空间映射" |
| 分块 Chunking | ① 语义/层级分块 vs 固定分块的忠实度差异 ② 父子块（small-to-big）如何兼顾召回与生成 ③ Contextual Retrieval 为什么能补回切块丢失的语境 | 用你自己的数据实测"固定分块 vs 标题层级切"的召回差异 |
| 混合检索 Hybrid | ① 稠密 vs 稀疏各自的强项/盲区 ② RRF 为什么比加权融合鲁棒 | 能举出"向量检索漏掉、BM25 能召回"的真实例子 |
| 重排 Rerank | ① cross-encoder vs bi-encoder 的本质区别 ② 为什么重排只对少量候选做 ③ 本地 reranker 的显存/延迟取舍 | 对比"嵌入重排 vs cross-encoder 重排"的 Top-3 命中率变化 |
| 生成 Generation | ① RAG 如何用上下文约束幻觉 ② 引用溯源的实现机制 ③ lost-in-the-middle 效应与首尾放置 | 设计一个"答案与资料一致性"的校验脚本 |
| 检索评估 Grader | ① 为什么要在检索后加质量评估（CRAG 原理）② 拒答/重试的阈值如何定 | 亲手实现一个检索质量评估器，验证纠正效果 |
| Agent | ① Function Calling 的协议本质 ② ReAct（Reason+Act）循环如何工作 ③ 工具返回如何影响下一轮推理 | 亲手写一个不带框架的 ReAct 循环 |

### 8.2 学习节奏建议

- **先通后精**：P1~P3 先跑通最小闭环（索引→检索→生成），再回头深挖每个模块原理
- **动手优先于阅读**：每个原理配合一个最小实验（如"去掉归一化会发生什么"），而非只看论文
- **记笔记沉淀**：每个模块学完写一段「原理 + 反例 + 实测数据」，最终汇总成个人知识库，这本身就是简历可展示的材料

## 九、工程质量与可量化指标（目标 ②：简历亮点）

> 本节是简历含金量的**核心**。面试官不信"我搭了个 RAG"，他信的是：**可复现的评估、可量化的性能、可审计的工程规范**。以下每一项做完，都是简历上一个可被追问的具体数字或能力点。

### 9.1 检索质量评估体系（自建指标 + 影子管线）

**要能回答的问题**："你的检索质量好不好？怎么证明？"

| 指标 | 含义 | 目标值 |
|---|---|---|
| 召回率 Recall@K | Top-K 里命中相关文档的比例 | > 0.8 @K=5 |
| 命中率 Hit Rate | 相关文档是否进入 Top-K | > 0.9 |
| MRR（平均倒数排名） | 第一个相关文档排第几 | > 0.7 |
| 生成忠实度 Faithfulness | 答案是否忠于检索到的资料 | > 0.9 |
| 答案相关性 Answer Relevance | 答案是否切题 | > 0.8 |
| 上下文精确度 Context Precision | 检索到的上下文信噪比 | > 0.8 |

**做法**：构造一个 50~100 条的标注评测集（问题 + 标准答案文档），用脚本自动跑出上述指标，并对比「纯向量 vs 混合检索 vs 混合+重排 vs 混合+重排+上下文检索」多档的效果差异——**这张"消融对比表"是面试时最有说服力的材料**。

**关键工程实践（RAGOps，2026 标准）**：

1. **Golden Dataset（黄金评测集）**：覆盖可回答/歧义/过时文档/应拒答四类边界问题，用真实用户问题而非臆造问题
2. **影子管线（Shadow Pipeline）评估**：每次部署前，新构建在影子管线跑一遍评测集，指标跌破阈值（如 Faithfulness < 0.9）则**阻断部署**——把评估做成 CI/CD 门禁，而非事后补课
3. **LLM-as-Judge**：用 qwen-max 作为独立裁判模型给"忠实度/相关性"打分（注意 judge bias，用黄金集校准）
4. **指标框架对照**：指标定义手写实现以理解原理，可选择性引入 RAGAS/DeepEval 做交叉校验（详见 §2.8 的取舍说明）

## 十、Agent 演进设计（从 RAG 到 Agent）

> 这是整个项目的**终局叙事**：RAG 不是终点，而是 Agent 的"记忆与工具"基座。把这一层设计清楚，项目就从一个"检索系统"升级为"完整的大模型应用"，这才是简历上真正有区分度的部分。

### 10.1 核心洞察：RAG 模块如何复用为 Agent 能力

| RAG 模块 | Agent 中的角色 | 复用方式 |
|---|---|---|
| 索引构建 Ingestion | Agent 的"长期记忆"写入 | 工具/知识入库，动态更新 |
| 检索 Retrieval | Agent 的"知识检索工具"（tool） | 封装为 `retrieve(query)` 工具 |
| 生成 Generation | Agent 的"推理/回答能力" | 复用 QWEN-MAX + Function Calling |
| 编排 Orchestration | Agent 的"执行循环"（ReAct 循环） | 把静态调度升级为动态规划 |
| 重排 Rerank | Agent 检索工具的质量保障 | 内嵌于 retrieve 工具 |

**一句话**：编排层（Orchestration）就是 Agent 的前身——把"固定调度"升级为"LLM 动态决策"，RAG 就变成了 Agent。

### 10.2 Agent 架构设计

```
┌─────────────────────────────────────────────────────┐
│                    Agent 主循环                      │
│   Reason（思考）→ Act（调用工具）→ Observe（观察结果） │
│           ↖_________________循环_________________↙    │
└──────┬──────────────────────────┬──────────────────┘
       │                          │
   推理能力                    工具层（Tool Registry）
   QWEN-MAX                  ├─ retrieve    （RAG检索工具）
   Function Calling          ├─ web_search  （联网搜索）
                             ├─ calculator  （计算）
                             └─ 自定义工具   （可扩展）
```

**关键设计点**：

1. **工具注册机制（Tool Registry）**：每个工具是「名称 + 描述 + JSON Schema 参数 + 执行函数」，用装饰器注册，Agent 通过 Function Calling 的 `tools` 参数暴露给 LLM
2. **ReAct 循环（手写，不用框架）**：`Thought → Action → Observation` 三步循环，直到 LLM 输出最终答案——这是理解 Agent 原理的必经之路，也是"手写底层"的延续
3. **RAG 检索工具化**：`retrieve` 工具内部调用已有的混合检索+重排管线，Agent 自动判断"这个问题需要先检索知识库"还是"直接回答"
4. **记忆系统**：短期记忆 = 对话历史（上下文窗口）；长期记忆 = 检索到的知识 + 已入库的知识库

### 10.3 与 LangChain 等框架的区别（也是卖点）

| 维度 | LangChain Agent | 本项目手写 Agent |
|---|---|---|
| 底层 | 封装黑盒，难看清 ReAct 细节 | 亲手实现循环、工具协议，原理通透 |
| 灵活性 | 受框架约束 | 完全可控，可自由扩展工具与策略 |
| 面试价值 | "我会用框架" | "我理解 Agent 底层机制，能脱离框架实现" |

### 10.4 Agent 阶段路线

| 阶段 | 内容 |
|---|---|
| A1 | 手写 ReAct 循环 + Function Calling 接入 QWEN-MAX |
| A2 | 把 RAG 检索封装为工具，实现"知识问答 Agent" |
| A3 | 扩展多工具（联网、计算、自定义），实现工具编排 |
| A4 | 加入记忆管理（多轮对话、长期知识） |
| A5 | 可选：多 Agent 协作（规划者 + 执行者） |

### 10.5 Agentic RAG 与 Adaptive RAG 的衔接（呼应 §3.4）

> 业界把 2026 年最大的范式转变称为 **Agentic RAG**——检索不再是固定管线里的一步，而是 Agent 自主决策的工具调用。本项目 §3.4 的自适应分层（L0~L3）正是通向 Agentic RAG 的**渐进式路线**：

1. **L2 多跳/迭代检索** = Agentic RAG 的雏形：编排层已具备"检索→评估→再检索"的循环能力（CRAG 的检索评估器即 Agent 的反思能力前身）
2. **L3 Agentic** = 完整 Agentic RAG：检索、评估、纠错全部由 LLM 动态决策，A1~A3 阶段实现
3. **关键衔接**：§3.4 的 CRAG 检索评估器（Grader）在 Agent 语境下就是"工具返回结果的质量判断"——它决定了 Agent 是继续检索、换工具、还是直接回答

**渐进式落地建议（业界共识）**：不要一步到位上完整多 Agent。先在 P5 编排层实现 CRAG（加一个检索评估节点），验证核心检索质量后，再到 P7 演进为完整 Agentic 循环。这与"手写底层、循序渐进"的定位一致，也避免了 Agentic 场景的工程复杂度与延迟失控（详见 §3.4 的成本提示）。

## 十一、索引生命周期管理（增量更新）

> 解决"索引建完之后，语料变了怎么办"。完整开发指引（注册表设计、四段增量流水线、代码结构、验证清单、常见坑）见 [P1-索引构建](dev-guide/P1-索引构建.md) §2.5。

**为什么单列**：demo 跑完一次就结束，生产系统里语料天天在变（新增/修订/下架）。本项目量级下全量重建约 21 小时（50 万块 ÷ 6.6 块/秒），改 1 篇文档却要撬动全库算力——这是企业级 RAG 与玩具 demo 的分水岭，也是 §9.3「数据管线」的具体设计。

**企业级方案分级（选型结论：L1）**：

| 方案 | 做法 | 时效 | 本项目 |
|---|---|---|---|
| L1 定时增量扫描 | cron + 内容 hash 比对，只 upsert 变更文档 | 分钟~小时 | ✅ 当前采用 |
| L2 事件驱动近实时 | Webhook / CDC → MQ → 消费端处理 | 秒级 | ⬜ 语料变活后演进 |
| L3 流式持续摄入 | Kafka 变更流直连处理管线 | 亚秒~秒级 | ⬜ 高频数据场景 |
| 兜底：蓝绿双索引 | Base + Delta 双索引，查询合并，compaction 切换 | 不停机 | ⬜ 大规模重建时 |

> 选型逻辑：先按数据源的变更捕获能力选 L1/L2/L3，再按规模决定是否叠加蓝绿。本项目单机 + 本地文件语料，无外部系统可订阅，**L1 即最优解**；但流水线按「变更检测 → 变更处理 → 索引写入 → 对账」四段搭建，升级 L2 只需替换第一段，后三段原样复用。

**本项目落地设计（保持 FAISS）**：

1. **文档注册表**（`data/index/registry.json`）：doc_id、content_hash（清洗后正文 SHA1）、version、chunk_ids、embedding_model、status，外加 `content_hash → doc_id` 的 **hash_index 反向索引**（服务"按内容判重"）——增量的一切建立在"有账本"上
2. **增量更新分两类来源**（见 [P1 §2.5.3.1](dev-guide/P1-索引构建.md)）：**A 存量文档变化**（`detect_changes` 目录 diff，做删除判定）与 **B 新文档注入**（`ingestor` 入站，按 content_hash 判重、不做删除）。二者共用「处理 / 写入 / 对账」内核，仅入口不同——解决"用户临时上传 / raw 之外路径新出现文档"的场景
3. **变更检测用内容 hash，不用 mtime**：git checkout / 解压会刷新 mtime 造成假变更，某些工具改内容不改 mtime 造成漏变更；hash 是内容本身，骗不了它
4. **文档级 diff**：hash 变 → 整篇重切重嵌（单篇 1~3 秒，可接受）；chunk 级 diff（块边界对齐、只重嵌变化块）作为进阶优化，触发条件见演进表
5. **软删除 + compaction**：`IndexFlatIP` 不支持单条删除，删除打 `deleted` 标记 + 检索侧过滤（P2 配合）；僵尸向量 >10% 触发 compaction——纯内存重组分钟级、不重嵌，这是 FAISS + 注册表的甜蜜点
6. **幂等与断点续传**：`doc_id + version` 幂等键、`job.json` 记录进度、单篇失败不阻断整批

**两条红线**：

- **换嵌入模型 = 全量重嵌 + 蓝绿切换**：新旧向量不在同一语义空间，混检会污染排序；注册表 `embedding_model` 字段即为此设计
- **软删除必须配合检索侧过滤**：否则下架内容仍可召回，属生产事故，过滤逻辑须有测试覆盖

**可量化指标**：增量更新延迟（单文档 <10s）、重嵌比例（变更块/总块，较全量省约 3 个数量级算力）、对账一致率（注册表 ↔ 索引，目标 100%）。

**与 Agent 衔接**：`updater.py`（类型 A）与 `ingestor.py`（类型 B）可分别封装为 Agent 的 `knowledge_update` / `knowledge_ingest` 工具，注册表的 hash/version 机制即 Agent 记忆的去重与版本管理（呼应 §10.1）。

**演进触发**：chunk 级 diff（单次增量 >10min）→ SQLite（注册表 >1 万条）→ Webhook/CDC（语料变活）→ 蓝绿双索引 → Qdrant/LanceDB（接口层已隔离）。
